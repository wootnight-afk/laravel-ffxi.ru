## 1. Цель и границы

**Цель.** Ввести постоянный активный персонаж аккаунта, единый серверный
`CharacterContext`, переключатель в боковом меню Players и независимый фильтр
игрового сервера.

**Входит:**

- хранение активного персонажа в БД (`user_active_characters`);
- `CharacterContext` и middleware разрешения контекста;
- переключение активного персонажа (Players и кабинет);
- фильтр сервера и его применение к существующей выдаче `players.directory`;
- граничные состояния и серверные проверки;
- локализация RU/EN, тесты, замеры геометрии, документация.

**Не входит:**

- персонажная атрибуция комментариев, чата, событий, новостей, activity
  (этап 3);
- каталог и публичные страницы персонажей (этап 4);
- галерея, фотографии, альбомы и любые их контроллеры, модели, маршруты,
  шаблоны и миграции;
- восстановление персонажей, лимит персонажей, Master Level;
- `users.active_character_id` и удаление legacy-колонок `users`;
- глобальный футер и настройки `footer.text_ru` / `footer.text_en`.

## 3. Схема данных (expand-only)

`game_characters`: добавляется **`UNIQUE (id, user_id)`** — дополнительный
уникальный ключ, на который опирается составной внешний ключ указателя.

Почему именно уникальный ключ, а не обычный индекс: в MySQL 8.4 переменная
`restrict_fk_on_non_standard_key` включена по умолчанию (в проектном окружении
проверено: MySQL 8.4.11, значение `ON`), поэтому внешний ключ, ссылающийся
на неуникальный индекс, создать нельзя. Отключение этой переменной —
устаревающий механизм, и как решение он не рассматривается: настройки сервера
не изменяются. Логически `UNIQUE (id, user_id)` тавтологичен (уникальность уже
обеспечена `PRIMARY KEY (id)`), но это требование MySQL к опорному ключу,
а не дополнительное ограничение модели. Затраты — один индекс на таблицу
персонажей.

`user_active_characters`:

| Колонка | Тип | Ограничение |
|---|---|---|
| `user_id` | BIGINT UNSIGNED | PK, FK → `users(id)` `ON DELETE CASCADE` |
| `character_id` | BIGINT UNSIGNED | NOT NULL, `UNIQUE` (инвариант «один персонаж — один аккаунт») |
| `created_at`, `updated_at` | timestamp | nullable |

Связь с персонажем — **единственный** внешний ключ, составной:
`(character_id, user_id) → game_characters(id, user_id)` `ON DELETE CASCADE`,
без `ON UPDATE`.

Правила схемы (вариант A, согласован 2026-11-18):

1. Отдельный обычный FK `character_id → game_characters(id)` **не создаётся**:
   составной ключ уже включает ссылочную целостность по `character_id` и даёт
   каскад, поэтому второй ключ дублировал бы ту же проверку и второй каскад
   на одну строку.
2. Триггеры не добавляются. Проверка владения не переносится в скрытую логику
   БД.
3. Настройки MySQL не изменяются: `restrict_fk_on_non_standard_key` остаётся
   `ON`, отключение не применяется.
4. Владение персонажем обеспечивается **самой БД**, а не только проверками
   приложения: записать в указатель чужого персонажа невозможно на уровне
   схемы. Серверные проверки в `CharacterContext` и Policy сохраняются, но
   выполняют роль диагностики и понятных кодов ответа, а не единственной
   гарантии.
5. Изменение владельца персонажа (`game_characters.user_id`) при наличии
   активного указателя отклоняется (`ON UPDATE` не задан). Передачи персонажей
   в проекте нет — это дополнительная защита, а не ограничение сценария.

Бэкфилл не выполняется: у аккаунтов без выбора состояние «персонаж не выбран».

### 3.1. Проверка DDL на MySQL 8.4 — обязательный критерий

1. `php artisan migrate --pretend` — просмотр SQL до применения.
2. Up/down на тестовой БД (`make test` использует отдельную БД).
3. `SHOW CREATE TABLE game_characters` и `SHOW CREATE TABLE user_active_characters`
   подтверждают: `UNIQUE (id, user_id)` на `game_characters`; на
   `user_active_characters` — PK `user_id`, `UNIQUE character_id`, FK `user_id`
   и единственный составной FK на `(id, user_id)` с `ON DELETE CASCADE`;
   обычного FK `character_id → game_characters(id)` нет; триггеров нет.
4. Значение `@@restrict_fk_on_non_standard_key` фиксируется в отчёте равным `ON`
   (настройка не меняется ни глобально, ни в сессии).
5. Результат (фактический DDL) прикладывается к отчёту этапа.

Согласованный вариант A обязателен. Если миграция на тестовой БД не создаёт
описанную схему, работа останавливается и оформляется отчёт о расхождении;
ослабление схемы (обычный индекс вместо уникального ключа, дополнительный FK,
триггер, изменение настроек MySQL) без нового согласования не допускается.

## 4. Серверная часть

### 4.1. `App\Services\CharacterContext`

Единственная точка определения активного персонажа.

| Метод | Поведение |
|---|---|
| `for(?User): ?GameCharacter` | `null` для гостя; читает указатель, проверяет владение, `deleted_at`, состояние аккаунта; кэш в пределах запроса; БД не пишет |
| `set(User, GameCharacter): void` | проверка владения и `deleted_at` под `lockForUpdate` + атомарная запись указателя по PK в одной транзакции; сброс кэша |
| `clear(User): void` | удаление строки, сброс кэша |
| `refresh(): void` | сброс кэша запроса (Livewire, повторное чтение) |
| `forget(User): void` | снятие указателя; вызывается из обработчика удаления; собственной транзакции не открывает |

Правила: контроллеры и шаблоны не определяют персонажа самостоятельно;
`character_id` принимается только в явном переключении; `CharacterTransaction`
не переиспользуется (он про запись персонажа и не реентерабелен).

### 4.2. Middleware `ResolveCharacterContext`

- регистрируется в группе `web` после `IdentifyGuest` и `SetLocale`;
- для гостя — no-op;
- для авторизованного — один запрос указателя + eager load `character.server`,
  результат в `View::share('activeCharacter', ...)`;
- записей в БД не делает;
- не подменяет `section.access` и `mfa.required`.

Данные для самого переключателя (персонажи аккаунта, активные серверы, фильтр)
middleware не грузит: их отдаёт read-only `App\Services\CharacterSwitcher`,
вызываемый из партиала панели.

### 4.3. Фильтр сервера

`App\Services\ServerFilter`: чтение/запись `session('players.server_filter')`
(slug), валидация по активным серверам, сброс. Не обращается к
`CharacterContext` и к таблице указателя.

### 4.4. Маршруты (в существующей группе Players)

| Метод | URL | Имя | Доп. middleware |
|---|---|---|---|
| POST | `/players/active-character` | `players.active-character.store` | `verified`, `throttle:30,60` |
| DELETE | `/players/active-character` | `players.active-character.destroy` | `verified`, `throttle:10,60` |
| POST | `/players/server-filter` | `players.server-filter.update` | `throttle:30,60` |

Группа уже содержит `auth`, `section.access:players`, `mfa.required`.
Ответ — redirect (PRG) с fallback на `players.dashboard`.
`SitePageRegistry` не меняется: не-GET классифицируется как `write`.

### 4.5. Коды ответов

| Ситуация | Ответ |
|---|---|
| Поле отсутствует / не число | 422 (JSON), 302 + ошибки валидации (браузерная форма) |
| Чужой персонаж | 404 |
| Удалённый (soft delete) персонаж | 404 |
| Несуществующий id | 404 |
| Состояние аккаунта запрещает операцию | 403 |
| Успех | 302 + redirect |

404 для трёх случаев намеренно неразличим: 403 подтверждал бы существование
чужого персонажа.

## 5. Граничные случаи

| Ситуация | Поведение |
|---|---|
| Нет персонажей | «нет персонажей» + ссылка на `/cabinet/characters` |
| Персонаж не выбран | «персонаж не выбран» + список, контекст `null` |
| Активный персонаж soft-deleted | Указатель снят в транзакции удаления, контекст `null`, UI «не выбран» |
| Указатель «осиротел» (удаление вне приложения) | Резолвер → `null`; GET строку не переписывает |
| Персонаж на деактивированном сервере | Остаётся активным и отображается |
| Персонаж стал непубличным | Контекст сохраняется |
| Аккаунт suspended / deletion_requested / banned | Контекст `null`, переключение 403 |
| Две вкладки | Одна строка (PK), побеждает последнее явное действие |
| Фильтр ссылается на деактивированный сервер | Игнорируется как «все», сессия на GET не перезаписывается |
| `restore` персонажа | Активным не становится |

## 6. Интерфейс

### 6.1. Блок в меню Players

`.players-section-nav__footer` (плашка «Раздел сообщества») заменяется блоком
`.players-context`:

- `__current` — `Аккаунт / Сервер / Персонаж` или «персонаж не выбран»;
- `__switcher` — форма POST: `<select name="character_id">` + «Переключить»;
- `__link` — «Мои персонажи» → `cabinet.characters.index`;
- `__filter` — форма POST: `<select name="server">` + «Применить»;
- `__note` — «Выбран другой сервер» + «Сбросить фильтр» (только отображение).

Требования: `@csrf`, `aria-label`, клавиатурная доступность, видимый фокус,
работа без JS, только токены цвета проекта, все подписи из `lang/{ru,en}`.
Текущий персонаж помечен `selected` и `aria-current`.

### 6.2. Мобильное поведение

Блок структурно независим от `__footer` и не включается в селектор скрытия,
поэтому виден на всех ширинах. `.players-section-nav` остаётся
`flex-direction: column`; на `≤1023px` блок встаёт под горизонтальным списком.
`margin-top: auto` сохраняет прижатие к низу на desktop и сбрасывается в `0`
на мобильных. Существующие правила `__brand`, `__footer`, `__list` и весь
мобильный блок не изменяются.

### 6.3. Кабинет персонажей

В списке и на странице персонажа: маркер «активный» и кнопка «Сделать
активным» (POST на тот же эндпоинт). Второго механизма переключения нет.

## 8. Атомарность удаления активного персонажа (обязательный критерий)

- Основная точка — `GameCharacterSaver::delete()`: soft delete персонажа и
  `CharacterContext::forget()` выполняются в одной транзакции
  `CharacterTransaction`.
- Сбой на любом шаге откатывает обе операции: недостижимы состояния
  «персонаж удалён, но активен» и «указатель снят, персонаж не удалён».
- `GameCharacterObserver::deleting` — идемпотентная страховка для путей вне
  `GameCharacterSaver`; собственной транзакции не открывает.
- Тест: исключение внутри транзакции удаления откатывает `deleted_at`
  и состояние указателя.

## 9. Безопасность

- CSRF на POST/DELETE; `throttle`; `verified` на переключение;
  `mfa.required` и `section.access` наследуются группой.
- Ownership проверяется на сервере при каждом действии; 404 вместо 403
  для чужих id.
- `user_id` персонажа не берётся из запроса и не участвует в массовом
  присваивании.
- **Владение персонажем гарантируется схемой БД**, а не только проверками
  приложения: составной FK `(character_id, user_id) → game_characters(id, user_id)`
  делает запись чужого персонажа невозможной даже при прямом `INSERT`/`UPDATE`
  в обход приложения. Серверные проверки в `CharacterContext` и Policy остаются
  и отвечают за понятные коды ответа и диагностику, но не являются единственной
  гарантией.
- Один путь записи указателя (`CharacterContext`); один путь записи
  персонажа (`CharacterTransaction` / `GameCharacterSaver`).
- Значение фильтра валидируется по активным серверам.
