## 0. Цель, границы, определение готовности

**Цель.** Перенести управление игровыми персонажами из раздела Players в кабинет,
довести модель персонажа до целевой (раса, main job, jobs и уровни, легенда),
сохранив все существующие данные, ссылки и уровень защиты.

**Границы.**

- Входит: маршруты и страницы кабинета, навигация, игровые поля персонажа,
  валидация, локализация, стили, тесты, alias старого URL, инструмент
  переноса legacy-игровых данных (подфаза 1.5, применяется отдельно).
- Не входит: активный персонаж и его хранение, переключатель в sidebar Players,
  фильтр игрового сервера, атрибуция комментариев/чата/событий/activity,
  публичные страницы персонажей, галерея, восстановление удалённых персонажей,
  лимит персонажей на аккаунт, Master Level.

**Определение готовности.** Все критерии §8 выполнены; `pest` зелёный; Pint и
Larastan чистые; подфаза 1.5 либо явно отложена владельцем, либо применена с
отчётом `--dry-run` и последующим подтверждением.

## 1. Аудит незакоммиченного Stage 0/1 Players

Проверено по фактическому коду, а не по отчётам. Незакоммиченный код **не
считается принятым**: ниже — вердикт по каждому элементу.

### 1.1. Что уже сделано и пригодно к переиспользованию

| Элемент | Факт | Вердикт |
|---|---|---|
| `game_servers` | справочник: `name`, `slug`, `description`, `sort_order`, `is_active`; уникальность `name`/`slug`; `GameServer::scopeActive/scopeOrdered` | **Принято без изменений** |
| `game_characters` | `user_id` (FK cascade), `game_server_id` (FK restrict), `name(24)`, `is_public`, `timestamps`, `deleted_at`; `unique(game_server_id, name)`; `index(user_id, deleted_at)` | **Принято**, расширяется (§3) |
| Владение персонажем | единственный источник — `game_characters.user_id`; `user_id` никогда не принимается из запроса | **Принято**, соответствует ADR-013 §2.1 |
| `GameCharacterPolicy` | `viewAny` — true; `view`/`update`/`delete` — владелец; `create` — verified и не забанен | **Принято**, дополняется проверкой секции в UI (§5) |
| Уникальность имени | case-insensitive через collation + проверка `withTrashed()` в `after()` валидатора | **Принято**, логика сохраняется |
| `scopePublic` | `is_public = true` и владелец в статусе `Active` | **Принято**, используется в будущих этапах |
| Server CRUD через админку | `GameServer` — Filament-ресурс, деактивация вместо удаления | **Принято** |

### 1.2. Что не соответствует целевой архитектуре и требует изменения

| # | Несоответствие | Требование |
|---|---|---|
| A1 | Управление персонажами живёт в `/players/characters`, а не в кабинете | §2: перенос в `/cabinet/characters*` |
| A2 | У персонажа нет расы, main job, jobs и уровней, легенды | §3: расширение модели |
| A3 | Игровые поля существуют только на `users` (`race`, `main_job`, `legend`, `legend_html`) | §6: перенос подфазой 1.5 без потери данных |
| A4 | Пункт «Мои персонажи» в `players/_sidebar` и `players/_section-nav` | §2.4: убрать из Players |
| A5 | `SitePageRegistry` содержит `players.characters.index` | §2.5: заменить записью кабинета |
| A6 | Метка `my_characters` отсутствует в `lang/{ru,en}/filament.php` | §7: добавить метки реестра |
| A7 | Нет страницы отдельного персонажа: список и редактирование в одном `details` | §2.2: отдельная страница `/cabinet/characters/{character}` |
| A8 | `Rule::exists(GameServer::class)->where('is_active', true)` блокирует сохранение персонажа на деактивированном сервере | §3.5: разрешать текущий сервер персонажа |
| A9 | Нет ограничения частоты на создание/изменение персонажа | §5.4: throttle |
| A10 | Тесты привязаны к маршрутам `players.characters.*` | §8: перенос в `tests/Feature/Cabinet` |

### 1.3. Что нельзя потерять при реализации

Незакоммиченный код является единственной копией Stage 0/1. Запрещено:
удалять `game_servers`/`game_characters` миграции и фабрики, менять их
`down()` в сторону потери данных, «пересоздавать» `GameCharacterPolicy`,
`StoreGameCharacterRequest`, `UpdateGameCharacterRequest` с нуля вместо
расширения, откатывать `User::gameCharacters()`, `GameServerSeeder`,
`tests/Feature/Players/GameCharacterTest.php` до реализации.

Допустимо: расширять перечисленные файлы, перемещать контроллер и шаблоны с
сохранением логики, переносить тесты с сохранением сценариев.

Посторонние файлы рабочей директории (временные скрипты и дампы в корне
репозитория, не относящиеся к Stage 0/1) в этом этапе не удаляются, не
перемещаются и не переформатируются. Реализация не выполняет `git clean`,
`git checkout`, `git stash` и `git reset`.

## 2. Структура кабинета и маршруты

### 2.1. Маршруты

| Метод | URI | Имя | Назначение |
|---|---|---|---|
| GET | `/cabinet/characters` | `cabinet.characters.index` | список персонажей + форма добавления |
| GET | `/cabinet/characters/{character}` | `cabinet.characters.show` | страница персонажа: данные, редактирование, удаление |
| POST | `/cabinet/characters` | `cabinet.characters.store` | создание |
| PUT | `/cabinet/characters/{character}` | `cabinet.characters.update` | сохранение |
| DELETE | `/cabinet/characters/{character}` | `cabinet.characters.destroy` | soft delete |
| GET | `/players/characters` | `players.characters.index` (alias) | 302 → `cabinet.characters.index` |

**Группа middleware.** Все маршруты персонажей, включая alias, сохраняют
текущую матрицу доступа:

```
['auth', 'section.access:players', 'mfa.required']      // чтение
['auth', 'section.access:players', 'mfa.required', 'verified'] // запись
```

Обоснование: перенос не должен ни расширять, ни сужать доступ. У роли `user`
право `section.players.view` есть (`RoleAndPermissionSeeder`), поэтому обычный
пользователь проходит; админ проходит по `Gate::before`. Пользователь с
настроенной MFA получает штатный редирект на `mfa.challenge` и возвращается
обратно — то же поведение, что сейчас в Players.

**Порядок регистрации.** Явные маршруты персонажей регистрируются **до**
`Route::get('/{tab}')` в группе `cabinet`, а alias `/players/characters` — **до**
`/players/{user:name}`, иначе ник `characters` перехватит адрес.

**Почему `characters` не добавляется в `CabinetController::TABS`.**
`TABS` управляет `whereIn` catch-all-маршрута `/cabinet/{tab}` и генерацией
`cabinet.tab.<tab>` в реестре страниц. Страница персонажа имеет собственный
контроллер, собственные middleware и два уровня вложенности. Добавление в
`TABS` создало бы второй маршрут на тот же URL и конфликт имён. Вкладка
кабинета при этом всё равно существует — она описана в массиве навигации
(§2.4) и в реестре страниц (§2.5).

**Старые write-маршруты.** `players.characters.store|update|destroy` удаляются.
POST/PUT/DELETE на `/players/characters*` после удаления дают 405 (маршрут
существует только для GET) — действие не выполняется ни при каких условиях.

### 2.2. Страницы и сценарии

**`/cabinet/characters` — список персонажей.**

- Заголовок «Мои персонажи», кнопка/ссылка «Добавить персонажа».
- Карточки: имя, сервер, публичность, ссылка «Открыть» → страница персонажа.
- Пустое состояние: «У вас пока нет добавленных персонажей» + форма добавления.
- Нет активных серверов: «Список игровых серверов пока пуст…», форма скрыта.
- Ссылка «Назад в кабинет» и сохранение общей навигации кабинета.
- Сортировка: по серверу (`sort_order`, `name`), затем по нику — стабильная и
  предсказуемая при нескольких серверах.

**`/cabinet/characters/{character}` — страница персонажа.**

Одна страница управления (просмотр + редактирование):

1. Заголовок: ник и сервер.
2. Форма данных: ник, сервер, публичность, раса, main job, jobs и уровни,
   легенда (Markdown).
3. Блок «Опасная зона»: soft delete с подтверждением.
4. Подсказка о Markdown (bold, italic, списки, ссылки) — переиспользуется
   существующий текст кабинета.
5. Ссылка «К списку персонажей».

Владелец чужого персонажа получает 403 (implicit binding + Policy). Скрытый
персонаж доступен владельцу — публичность влияет только на публичные выдачи.

**Сценарии.**

- Пользователь без персонажей: кабинет → «Мои персонажи» → пустое состояние →
  добавление → карточка в списке.
- Пользователь с персонажами: список → страница персонажа → правка легенды и
  jobs → сохранение → возврат на страницу с сообщением.
- Пользователь удаляет персонажа: подтверждение → soft delete → список →
  сообщение; имя остаётся занятым на сервере (ADR-012 §2.3).
- Пользователь открывает старую закладку `/players/characters` → 302 → кабинет.
- Пользователь без права `section.players.view` → 403 (как сейчас).

### 2.3. Навигация кабинета

Порядок вкладок: **Профиль → Мои персонажи → Социальные сети → Новости →
Галерея → События → Безопасность → Опасная зона**.

Реализация: в `resources/views/cabinet/show.blade.php` массив навигации
переводится в форму `key => ['label' => …, 'route' => …]`, чтобы вкладка
персонажей вела на `cabinet.characters.index`, а остальные — на
`cabinet.tab`. Пункт «Мои персонажи» показывается только если у пользователя
есть доступ к секции (`@can('section.players.view')`) и маршрут
зарегистрирован — иначе пользователь видел бы пункт, ведущий на 403.

### 2.4. Навигация Players

- `players/_sidebar.blade.php`: пункт `players.characters.index` удаляется.
- `players/_section-nav.blade.php`: пункт из группы «Мой аккаунт» удаляется;
  ссылка «Личный кабинет» остаётся и ведёт в `/cabinet`.
- Переход к управлению персонажами из Players не дублируется: второе место
  управления запрещено. Допустимая точка входа — пункт «Личный кабинет».
- Геометрия Players sidebar (§11 `designreview.md`) не затрагивается: правки
  касаются только массива пунктов, не разметки каркаса и не CSS.

### 2.5. Реестр страниц

- `SitePageRegistry::PAGES`: запись `players.characters.index` заменяется на

`Hume`, `Elvaan`, `Tarutaru`, `Mithra`, `Galka`; значение — нижний регистр

22 кода FFXI: `WAR, MNK, WHM, BLM, RDM, THF, PLD, DRK, BST, BRD, RNG, SAM, NIN,

### 3.5. Сохранение данных персонажа

Порядок записи — одна транзакция:

1. Обновление скалярных полей (`name`, `game_server_id`, `is_public`, `race`,
   `main_job`).
2. `legend` сравнивается с текущим значением; `legend_html` пересчитывается
   только при изменении (как в `CabinetController::updateProfile`).
3. `jobs` синхронизируются: отсутствующие в запросе строки удаляются, новые
   создаются, существующие обновляются (`upsert` по
   `(game_character_id, job)`).

Валидация (общая для store и update, вынесена в трейт/базовый класс
`GameCharacterRequest`):

- `name`: `required|string|min:2|max:24` + проверка уникальности на сервере
  включая soft-deleted (существующая логика сохраняется);
- `game_server_id`: существует и активен **или** совпадает с сервером, уже
  сохранённым у этого персонажа в БД (исправление A8). Сравнение идёт с
  `$character->game_server_id` из базы, а не со значением из запроса — иначе
  правило обходится подстановкой любого неактивного сервера;
- при создании персонажа «текущего сервера» не существует: разрешены только
  активные серверы, создание на неактивном запрещено;
- смена сервера на неактивный запрещена всегда, включая случай, когда персонаж
  уже находится на другом неактивном сервере;
- `race`: `nullable` + `Rule::enum(CharacterRace::class)`;
- `main_job`: `nullable` + `Rule::enum(GameJob::class)` + входит в `jobs`;
- `jobs`: `array`; ключи — коды `GameJob`; значения `nullable|integer|min:1|max:99`;
  пустые значения отбрасываются в `prepareForValidation()`;
- `legend`: `nullable|string|max:4000`;
- `is_public`: `sometimes|boolean`;
- `user_id`, `id`, `deleted_at` в правилах отсутствуют.

`GameCharacter::$fillable` расширяется до
`['user_id', 'game_server_id', 'name', 'is_public', 'race', 'main_job', 'legend', 'legend_html']`.
`legend_html` пишется только сервером (из `ContentRenderer`), но не принимается
из запроса — в правилах валидации его нет.

### 3.6. Отображение

- Карточка в списке: ник, сервер, раса (или «не указана»), main job и его
  уровень, публичность.
- Страница персонажа: все поля, таблица jobs (только изученные), легенда —
  отрендеренный HTML с fallback «Легенда не заполнена».
- Jobs в форме: сетка 22 полей `number` (пусто = job не изучен), 2 колонки на
  desktop, 1 на mobile. Без JS-репитера и без Livewire: SSR-форма проще
  тестируется, работает без JavaScript и не добавляет зависимостей страницы.
- Select сервера в форме: активные серверы плюс текущий сервер персонажа, даже
  если он деактивирован. Такой сервер помечается подписью «сервер неактивен»,
  остаётся выбранным и не даёт сохранить смену на другой неактивный сервер.
  При создании персонажа список содержит только активные серверы.

## 5. Безопасность и права

### 5.1. Ownership

- Единственный источник владения — `game_characters.user_id`; значение из
  запроса игнорируется (существующее поведение сохраняется).
- `GameCharacterPolicy`: `view`, `update`, `delete` — только владелец; админ
  не получает неявного доступа к чужим персонажам через эти маршруты
  (администрирование идёт через Filament и аудит).
- Implicit route binding: чужой id → 403; soft-deleted персонаж → 404
  (штатное поведение Eloquent).

### 5.2. MFA

- Маршруты персонажей остаются под `mfa.required`, чтобы перенос в кабинет не
  снизил защиту: пользователь с настроенной MFA проходит штатный challenge.
- `cabinet/characters` не добавляется в escape-hatch `RequireMfa`.
- Остальные вкладки кабинета поведение не меняют.

### 5.3. Секция

- `section.access:players` сохраняется на всех маршрутах персонажей.
- Пункт навигации в кабинете показывается только при наличии права.
- При выключенной секции персонажи недоступны, но остальной кабинет работает.

### 5.4. Прочее

- `POST` создание и `PUT` обновление: `throttle:20,60`; `DELETE`:
  `throttle:10,60`.
- CSRF — штатный `@csrf`; формы только POST с `@method`.
- Подтверждение удаления — серверное (страница с кнопкой), без опоры на JS
  (`onsubmit=confirm` допустим как дополнительный UX, но не как защита).
- Логирование: ошибки валидации не логируются; факт удаления персонажа
  фиксируется в общем журнале активности администратора только при
  административном вмешательстве (в этом этапе таких действий нет).

### 5.5. Инвариант доступа: было → стало

| Проверка | Сейчас (`/players/characters*`) | После переноса (`/cabinet/characters*` + alias) |
|---|---|---|
| Аутентификация | `auth` | `auth` — без изменений |
| Секция | `section.access:players` | `section.access:players` — без изменений |
| MFA | `mfa.required` | `mfa.required` — без изменений |
| Подтверждённый email | `verified` на записи | `verified` на записи — без изменений |
| Владение | `user_id` + Policy | `user_id` + Policy — без изменений |
| Чужой id | 403 | 403 — без изменений |
| Soft-deleted персонаж | 404 | 404 — без изменений |

Ни одна строка таблицы не может стать слабее. Любое расхождение при ревью —
блокирующее замечание, а не повод «упростить» middleware.

## 6. Legacy-данные: подфаза 1.5 (отдельная операция)

Подфаза **не входит** в обычную реализацию Этапа 1: код инструмента пишется в
этапе, применение к данным — отдельная операция с отдельным подтверждением.

### 6.1. Что переносится

`users.race` → `game_characters.race`, `users.main_job` → `game_characters.main_job`,
`users.legend` → `game_characters.legend` (Markdown как есть), а
`game_characters.legend_html` формируется из перенесённого Markdown через
`ContentRenderer`, а не копированием HTML.

`users.legend_html` не копируется: он пересчитывается из Markdown, чтобы
исключить расхождение форматов и устаревшую санитизацию.

Правила для легенды при переносе и при обычном сохранении одинаковы:

- исходное содержимое — только `legend` (Markdown); `legend_html` никогда не
  является источником и не принимается из запроса;
- HTML формируется `ContentRenderer` (CommonMark + `HtmlSanitizer`,
  `html_input: strip`), то есть сырой HTML и опасные ссылки не проходят;
- рендер детерминирован: один и тот же Markdown даёт один и тот же HTML, и
  `legend_html` можно пересоздать из `legend` в любой момент;
- пустой `legend` даёт `null` в `legend_html`, а не пустую разметку;
- legacy `legend_html` без проверки не используется даже как fallback —
  расхождение устраняется пересчётом, а не доверием к старому полю.

### 6.2. Правила по количеству персонажей

| Персонажей у аккаунта | Действие |
|---|---|
| 0 | Не переносить. Данные остаются на аккаунте, попадают в отчёт «нет получателя» |
| 1 (не удалён) | Переносить по каждому полю: пустые — переносить, непустые — `skipped_conflict` |
| 2 и более | **Не переносить автоматически.** Владелец выбирает персонажа в кабинете (форма «Игровые данные аккаунта») |
| Есть только soft-deleted | Не переносить: удалённый персонаж не получает данные |

Дополнительно — правило действует по каждому полю, а не по персонажу целиком:

- поле переносится только если целевое поле персонажа `NULL` или пустая строка
  (после нормализации, §6.3.1);
- непустое целевое поле **не перезаписывается**: перенос по нему пропускается,
  конфликт фиксируется в журнале со статусом `skipped_conflict` и прежним
  значением `target_value_before`; остальные пустые поля того же аккаунта при
  этом переносятся;
- для `game_character_jobs` единица проверки — пара (персонаж, job): уровень
  переносится, только если строки этого job у персонажа ещё нет;
- конфликты видны в `--report` и `--dry-run` до применения и попадают в
  итоговый отчёт с разбивкой по полям, а не только в общее число пропусков;
- перезапись существующих значений — только явный режим `--overwrite`
  (§6.3.2), по умолчанию запрещена.

### 6.3. Инструмент

`php artisan characters:legacy-game-data` с режимами:

| Флаг | Поведение |
|---|---|
| `--report` | только статистика распределения (аккаунты с данными, по числу персонажей, потенциальные конфликты) |
| `--dry-run` | статистика + пофамильный список планируемых действий, **без записи** |
| `--apply` | запись в транзакции с записью в журнал; требует `--force` в production |
| `--overwrite[=поля]` | разрешает запись в непустые скалярные поля вместо `skipped_conflict`. Без значения — весь допустимый набор; со значением — список через запятую. Действует только вместе с `--apply`, в production — с `--force` (§6.3.2) |
| `--rollback={batch}` | откат конкретного пакета |

Требования к инструменту:

- идемпотентность: повторный `--apply` не создаёт дублей и не перезаписывает
  изменённое пользователем;
- пакет (`batch_id`) фиксируется для каждой записи;
- журнал `legacy_game_data_transfers` фиксирует обе стороны переноса и решение
  по каждому полю:

  | Колонка | Назначение |
  |---|---|
  | `batch_id` | пакет запуска либо ручного переноса |
  | `user_id`, `character_id`, `field`, `field_group` | адрес переноса; `field_group = legend` связывает `legend` и `legend_html` |
  | `status` | `applied`, `skipped_conflict`, `skipped_no_target`, `skipped_no_source`, `skipped_modified`, `reverted` |
  | `source_value`, `source_hash` | исходное значение аккаунта и **нормализованный** хеш — только для сопоставления при импорте |
  | `target_value_before`, `target_hash_before` | прежнее значение персонажа как есть и его **контрольный** хеш; `NULL`, если поле было пустым |
  | `applied_hash` | **контрольный** хеш фактически сохранённого значения — по нему откат отличает нетронутое поле от изменённого |
  | `applied_at`, `reverted_at`, `reverted_by`, `note` | аудит и причина решения |

- фиксируются обе стороны переноса: исходное значение аккаунта и прежнее
  значение персонажа. Этого достаточно и для проверки результата, и для
  отката, без доверия к текущему состоянию полей;
- `--rollback={batch}` обрабатывает только записи `applied` и восстанавливает
  `target_value_before` (для пустого прежнего значения — `NULL`) тогда и только
  тогда, когда текущий **контрольный** хеш поля совпадает с `applied_hash`;
  нормализованный `source_hash` для этого решения не используется;
- поля, изменённые после импорта, не перезаписываются и не обнуляются: запись
  переводится в `skipped_modified`, изменение сохраняется и попадает в отчёт;
- записи `skipped_*` откат не меняет: перенос по ним не выполнялся,
  восстанавливать нечего;
- откат идемпотентен: повторный запуск по тому же `batch_id` ничего не меняет,
  записи с заполненным `reverted_at` повторно не обрабатываются;
- единица транзакции — аккаунт и для `--apply`, и для `--rollback`: сбой на
  одном аккаунте не откатывает уже зафиксированные аккаунты и не оставляет
  текущий аккаунт перенесённым или восстановленным частично (§6.3.3);
- `--apply` по умолчанию пишет только в пустые целевые поля; заполненные
  значения персонажа не перезаписываются ни при первом запуске, ни при
  повторном. Запись в непустое поле возможна только в режиме `--overwrite`
  (§6.3.2) с сохранением прежнего значения в журнале;
- вывод — таблица чисел: просмотрено аккаунтов, перенесено значений по полям,
  пропущено с причинами (`0 персонажей` / `2+` / `уже заполнено` / `удалённый`),
  конфликтов с разбивкой по полям, ошибок;
- перед `--apply` в production обязателен свежий backup (существующая
  подсистема ADR-004); инструмент проверяет свежесть и предупреждает.

#### 6.3.1. Две независимые величины: нормализация импорта и контрольный хеш

Нормализация нужна, чтобы импорт не считал конфликтом уже перенесённое и не
различал `NULL` и `''`. Для контроля изменений она непригодна: она скрывает
именно те правки, которые нужно обнаружить. Поэтому в журнале две независимые
величины, и они никогда не подменяют друг друга.

**1. Нормализация импорта** (`source_hash`, проверка «целевое поле пустое»):

| Поле | Нормализация для импорта |
|---|---|
| `race` | trim, нижний регистр, пусто → «значение отсутствует» |
| `main_job` | trim, верхний регистр, пусто → «значение отсутствует» |
| `legend` | CRLF и CR → LF, trim, пусто → «значение отсутствует» |
| `legend_html` | не участвует: источником всегда остаётся `legend` |
| `game_character_jobs` | уровень `(int)` 1..99; пусто или 0 → строки нет |

- `NULL` и `''` для импорта эквивалентны — это «значение отсутствует»;
- решение «целевое поле пустое» принимается по этому же признаку, а не по
  строгому сравнению с `NULL`;
- нормализованный хеш используется только для сопоставления с исходным
  значением аккаунта и для отчёта.

**2. Контрольный хеш фактического значения** (`applied_hash`,
`target_hash_before`):

Считается по значению, которое реально лежит в БД: без trim, без смены
регистра, без приведения `''` к `NULL`.

```
control_hash = sha256(field . "\0" . tag . "\0" . payload)
```

| `tag` | Когда | `payload` |
|---|---|---|
| `null` | значение `NULL` | пусто |
| `str` | строка, включая `''` | точные байты значения |
| `int` | числовое (уровни jobs) | десятичная запись без ведущих нулей |

- `tag` различает `NULL` и `''`: переход `NULL` → `''` меняет контрольный хеш,
  хотя для импорта оба значения пустые;
- регистр и внешние пробелы входят в `payload`: правка `hume` → `Hume` или
  добавленный пробел в легенде обнаруживаются;
- `applied_hash` фиксируется **после** записи по значению, прочитанному из БД,
  а не по значению из запроса: журнал описывает фактическое состояние;
- `target_hash_before` считается тем же способом по прежнему значению
  персонажа, поэтому восстановление проверяемо.

**3. Применение по группам полей:**

- `race`, `main_job` — один контрольный хеш на поле;
- `legend` и `legend_html` — два контрольных хеша, связанные
  `field_group = legend`. Откат группы выполняется только если **оба** текущих
  хеша совпадают с `applied_hash`; расхождение любого переводит группу в
  `skipped_modified` целиком, чтобы не получить Markdown от импорта и HTML от
  пользователя (или наоборот);
- `game_character_jobs` — контрольный хеш строки
  `sha256("jobs" . "\0" . job . "\0int\0" . level)`; откат удаляет строку
  только при совпадении хеша и не затрагивает строки других jobs. Уровень —
  целое, поэтому `NULL`/`''` здесь не возникают: отсутствие job выражается
  отсутствием строки.

#### 6.3.2. Режим перезаписи (`--overwrite`)

Синтаксис ровно один — опциональное значение через `=`:

```
--overwrite                  # весь допустимый набор полей
--overwrite=race,legend      # перечисление через запятую
```

Допустимый набор — только скалярные поля персонажа: `race`, `main_job`,
`legend`. Никаких других имён режим не принимает.

Правила:

- `--overwrite` без значения означает весь набор `race`, `main_job`, `legend`;
- `legend` в списке означает группу: `legend` и производный `legend_html`
  записываются вместе; рассогласование пары не допускается;
- `legend_html` в списке — ошибка ввода: HTML не является самостоятельным полем
  и отдельно не выбирается;
- `game_character_jobs` этим режимом не перезаписываются никогда: указание
  `jobs` — ошибка ввода, существующие уровни не меняются ни при каких флагах;
- неизвестное имя поля и пустое значение (`--overwrite=`) — ошибка ввода;
  команда завершается без записи;
- режим действует только вместе с `--apply`; без него — ошибка, а не «тихое»
  игнорирование; в production дополнительно требуется `--force`.

Что попадает в журнал при перезаписи:

| Величина | Содержимое |
|---|---|
| `source_value`, `source_hash` | исходное значение аккаунта и его нормализованный хеш |
| `target_value_before` | прежнее значение персонажа как есть, включая `NULL` |
| `target_hash_before` | контрольный хеш прежнего значения |
| `applied_hash` | контрольный хеш фактически записанного значения |

Условия безопасного восстановления:

- `--rollback` возвращает `target_value_before`, а не `NULL`;
- восстановление выполняется только при совпадении текущего контрольного хеша
  с `applied_hash`;
- для группы `legend` условие проверяется по обоим хешам, иначе группа не
  восстанавливается;
- если поле или группа менялись после перезаписи — `skipped_modified`,
  пользовательское значение остаётся;
- повторный `--rollback` по тому же `batch_id` уже восстановленные и изменённые
  записи не трогает;
- без `--overwrite` непустое поле даёт `skipped_conflict`, значение персонажа
  остаётся прежним.

#### 6.3.3. Конкурентный откат: транзакция, блокировки, ошибки

Проверка контрольного хеша и запись восстановления — одна атомарная операция.
Если между ними успеет пройти чужая правка, откат затрёт её. Поэтому проверка и
запись выполняются в одной транзакции, а строка персонажа блокируется.

**Единица и порядок.**

- Транзакция — на аккаунт (как и у `--apply`): один-два персонажа, до шести
  полей, без внешних вызовов внутри (HTTP, файлы, backup — до транзакции).
- Порядок захвата фиксирован: персонажи по возрастанию `id`, затем строки
  `game_character_jobs` по возрастанию `job`, затем записи журнала по `id`.
  Единый порядок исключает взаимные блокировки между `--apply` и `--rollback`
  и между двумя запусками отката.
- Уровень изоляции — штатный для проекта (`REPEATABLE READ`); глобально менять
  его не требуется, сериализацию даёт блокировка строки персонажа.

**Единый механизм записи (обязательный инвариант).**

Блокировка защищает только тогда, когда её берёт каждый, кто пишет. При этом
«единственный класс на всё» здесь неверен: у пользовательского сохранения,
импорта и отката разные правила полей, и общий сервис начал бы смешивать их
либо требовать флагов, отключающих собственную защиту. Инвариант двухуровневый.

**Уровень 1 — один механизм транзакций и блокировок.**

`App\Services\CharacterTransaction` — единственное место, где открывается
транзакция записи персонажей и берутся блокировки:

- `run(User $account, Closure $operation)` — операция записи аккаунта. Кто
  владеет транзакцией и кто отвечает за commit/rollback, определяется уровнем
  вложенности на входе (§6.3.4):

  | `DB::transactionLevel()` на входе | Режим | Commit / rollback | Повторы |
  |---|---|---|---|
  | `0` | владелец | механизм: `beginTransaction` → `commit` / `rollBack` | да |
  | `> 0` | присоединение | владелец внешней транзакции; механизм откатывает только свою операцию до savepoint | нет |

- рекурсивный вход — вызов `run` изнутри уже выполняющейся операции
  `CharacterTransaction` — даёт `LogicException`: две политики полей в одной
  операции смешивать нельзя. Это единственный случай исключения; наличие
  внешней транзакции (например, `RefreshDatabase` в тестах) исключением не
  является;
- `lockCharacter(int $id)` и `lockCharacters(array $ids)` — `lockForUpdate` по
  PK в порядке возрастания `id`, возвращают актуально прочитанную строку
  (current read);
- `lockJobs(int $characterId)` — `FOR UPDATE` по `(character_id, job)` в порядке
  `job`;
- блокировки удерживаются до коммита или отката всей транзакции аккаунта:
  механизм не освобождает их между шагами и не дробит одну операцию на
  несколько транзакций;
- внутри `run` запрещены внешние вызовы (HTTP, файлы, backup) — только БД;
- несколько полей и несколько jobs изменяются в одной транзакции аккаунта,
  поэтому набор применяется атомарно.

**Уровень 2 — специализированные операции поверх механизма.**

| Операция | Класс | Правила полей |
|---|---|---|
| Пользовательское сохранение персонажа и jobs | `GameCharacterSaver` | Валидация формы, запрет перезаписи непустых полей, `is_public`, soft delete |
| Импорт legacy-данных (`--apply`, ручной перенос) | `LegacyGameDataImporter` | Только пустые поля либо режим `--overwrite`, журнал переноса |
| Откат импорта (`--rollback`) | `LegacyGameDataRollback` | Восстановление `target_value_before`, удаление импортированных jobs по контрольному хешу |

Все три вызывают `CharacterTransaction` и не открывают транзакции
самостоятельно. Прямые `DB::beginTransaction()`, `DB::transaction()` и
`lockForUpdate()` по `game_characters` / `game_character_jobs` вне
`CharacterTransaction` запрещены.

| Путь изменения | Правило |
|---|---|
| HTTP `Cabinet\CharacterController` + Form Requests | `GameCharacterSaver` |
| Livewire-компоненты и Actions (включая будущие этапы 2–3) | `GameCharacterSaver` |
| Filament | Ресурса персонажей нет и в этапе 1 не создаётся. Если появится — action, вызывающий `GameCharacterSaver`; наблюдатели и прямые `->update()` недопустимы |
| Консольные команды, импортёр, фоновые задания | `LegacyGameDataImporter` / `LegacyGameDataRollback`, а не `GameCharacterSaver` |
| Фабрики и сидеры | Тестовые и начальные данные; production-путём не являются, механизм не используют |

Почему импортёр и откат не идут через `GameCharacterSaver`: у них другие
правила записи — перезапись непустых полей, восстановление прежних значений,
удаление jobs по журналу. Выражение этих операций через пользовательский сервис
смешало бы две ответственности. Общими для всех трёх остаются транзакция,
блокировки, порядок захвата и границы — то есть `CharacterTransaction`.

Запрещено вне `CharacterTransaction` и фабрик/сидеров:
`GameCharacter::create|insert|upsert|firstOrCreate|updateOrCreate`,
`->save(`, `->saveQuietly(`, `->update(`, `->delete(`, `->forceDelete(`,
`->restore(`, `->push(`, `->increment(`, `->decrement(` для персонажа,
`DB::table('game_characters')`, `DB::table('game_character_jobs')`,
`DB::statement(`, `DB::update(` с этими таблицами, а также запись jobs через
`jobs()->create|save|sync|delete`.

Фактическое состояние на момент подготовки ТЗ: в коде есть только
`MyCharactersController`; Filament-ресурса персонажей и Livewire-компонентов
персонажей нет. Правило фиксируется на будущее, чтобы новый путь не обошёл
блокировку.

Контроль исполнения — §8.3: архитектурный тест границ зависимостей (какие
классы вообще вправе ссылаться на модели персонажей), тест примитивов записи
(обход через `insert`/`upsert`/`DB::table`/`saveQuietly`) и поведенческие тесты
точки входа. Текстовый поиск по `app/` используется как вспомогательный слой, а
не как единственный механизм.

Следствие: импорт, откат и пользовательская правка сериализуются одной и той же
блокировкой строки и подчиняются одним правилам транзакций; обходного пути
записи нет, а набор полей и jobs применяется атомарно в транзакции аккаунта.

**Что блокируется.**

| Объект | Блокировка | Зачем |
|---|---|---|
| `game_characters` (строка персонажа) | `SELECT ... FOR UPDATE` по PK (`lockForUpdate()`) | Все скалярные поля и группа `legend` восстанавливаются под одной блокировкой — конкурентная правка ждёт |
| `game_character_jobs` (строка job) | `SELECT ... FOR UPDATE` по `(game_character_id, job)` | Уровень читается и удаляется под блокировкой: изменение уровня не проскочит между проверкой и `DELETE` |
| `legacy_game_data_transfers` (запись журнала) | `UPDATE ... WHERE id = ? AND status = 'applied' AND reverted_at IS NULL` | Смена статуса — атомарный шаг: 0 затронутых строк означает, что запись уже обработана параллельным запуском |

**Порядок шагов внутри транзакции аккаунта.**

1. `FOR UPDATE` по строке персонажа.
2. **Current read**: значения полей читаются тем же locking-read запросом (или
   сразу после него в этой транзакции) — из БД, а не из памяти процесса.
3. Пересчёт контрольных хешей по этим значениям и сравнение с `applied_hash`;
   несовпадение → `skipped_modified` без записи в поля.
4. Запись `target_value_before`, смена статуса записи журнала на `reverted` с
   `reverted_at` и `reverted_by`.
5. Коммит.

Запрет на устаревшие данные: решение об откате нельзя принимать по

- Eloquent-модели, загруженной до начала транзакции (значения в памяти могли
  устареть);
- обычному `SELECT`, выполненному до `FOR UPDATE`: в `REPEATABLE READ` он
  вернёт snapshot-версию, а не текущую;
- `fresh()`/`refresh()` без блокировки — они не заменяют locking read и не
  защищают от гонки между чтением и записью;
- коллекциям и отношениям, загруженным вне транзакции.

В InnoDB `SELECT ... FOR UPDATE` — это current read: он читает последнюю
закоммиченную версию строки и блокирует её. Поэтому хеш, посчитанный по данным
locking read, соответствует именно тому состоянию, которое перезаписывается в
шаге 4.

Шаги 2–4 идут в одной транзакции, поэтому TOCTOU («проверили одно, записали
поверх другого») невозможен: параллельная правка либо завершится до блокировки,
либо будет ждать коммита.

**Группа `legend` / `legend_html`.**

- Обе записи журнала читаются, оба поля пишутся в одной транзакции под
  блокировкой строки персонажа.
- Условие входа в восстановление — совпадение **обоих** контрольных хешей;
  иначе группа целиком переводится в `skipped_modified`, и ни одно из полей не
  меняется.
- Частичного восстановления не бывает структурно: `legend` и `legend_html`
  входят в один `UPDATE` строки персонажа, а не в два независимых запроса.

**`game_character_jobs`.**

- Удаление выполняется по журнальной записи `(character_id, job)` после
  `FOR UPDATE` этой строки.
- В самом `DELETE` повторяется условие: `WHERE game_character_id = ? AND
  job = ? AND level = ?` (уровень из журнальной записи). Изменённый уровень не
  удаляется даже при гонке.
- Строки других jobs не затрагиваются: `DELETE` ограничен одной парой.

**Ошибки, deadlock, повторный запуск.**

- Любое исключение внутри транзакции аккаунта (deadlock, `lock wait timeout`,
  ошибка записи) откатывает её целиком: ни поля персонажа, ни статусы журнала
  по этому аккаунту не меняются. Частично восстановленного аккаунта не
  возникает.
- Повторяются только transient-ошибки: deadlock (MySQL 1213) и
  `lock wait timeout` (1205). Ошибки валидации, нарушения инвариантов и прочие
  логические сбои не повторяются — они сразу помечаются как ошибка аккаунта.
- Повторы выполняет только владелец транзакции (режим
  `transactionLevel() = 0`): не более трёх попыток на аккаунт с нарастающей
  паузой, каждая попытка — новая транзакция аккаунта, изменения предыдущей
  откатываются целиком.
- В режиме присоединения повторов нет: deadlock (1213) отменяет всю внешнюю
  транзакцию, поэтому решение о повторе принимает её владелец, а механизм
  пробрасывает исключение наверх. `lock wait timeout` (1205) по умолчанию
  откатывает только statement — механизм в этом режиме тоже не повторяет, чтобы
  не выполнить операцию дважды в чужой транзакции.
- После исчерпания попыток транзакция аккаунта откатывается целиком, поэтому ни
  одно поле персонажа и ни один статус журнала по этому аккаунту не остаётся
  изменённым: частично откатанного аккаунта не существует.
- Ошибка аккаунта фиксируется **вне отменённой транзакции** — отдельной
  транзакцией после rollback (`note` в журнале либо отдельная запись отчёта).
  Запись об ошибке внутри отменённой транзакции недопустима: она исчезнет
  вместе с откатом. Если отдельная запись тоже не удалась, ошибка остаётся в
  отчёте запуска и логе, данные при этом не затрагиваются.
- Обработка продолжается со следующего аккаунта; ошибка одного аккаунта не
  прерывает `batch`.
- Повторный запуск после ошибки безопасен: выборка берёт только аккаунты, у
  которых остались записи в статусе `applied`; `reverted` пропускаются,
  `skipped_modified` не пересматриваются, неизменённые `applied` обрабатываются
  заново по тем же правилам. Уже успешно откатанные аккаунты повторно не
  обрабатываются.
- Параллельный второй `--rollback` по тому же `batch_id` ничего не восстановит
  дважды: статус меняется атомарным `UPDATE ... WHERE status = 'applied'`, и
  проигравший видит 0 затронутых строк.
- Правка персонажа в кабинете использует ту же блокировку строки
  (`GameCharacterSaver` через `CharacterTransaction`), поэтому «проверка →
  запись» отката и сохранение формы сериализуются: либо правка попадёт в
  контрольный хеш и откат её пропустит, либо откат завершится раньше и правка
  ляжет поверх восстановленного значения — но не наоборот.

### 6.3.4. Вложенность, savepoints и владение транзакцией

Laravel не создаёт настоящую вложенную транзакцию: при `transactionLevel() > 0`
`DB::transaction()` открывает `SAVEPOINT transN`, commit вложенного уровня лишь
освобождает savepoint, а реальный `COMMIT` происходит только на уровне 1.
`CharacterTransaction` следует этому поведению, а не борется с ним.

**Кто чем владеет.**

- Вызов на уровне 0: механизм — владелец. Открывает транзакцию, коммитит при
  успехе, откатывает при исключении, выполняет повторы (§6.3.3) и фиксирует
  ошибку аккаунта уже после отката.
- Вызов внутри внешней транзакции (`> 0`): владелец — внешний код (контроллер,
  команда, тест с `RefreshDatabase`). Механизм **не** коммитит и **не**
  откатывает всю транзакцию: при исключении он откатывается до своего
  savepoint, оставляя работу владельца целой, и пробрасывает исключение наверх.
- Рекурсивный вход внутрь выполняющейся операции запрещён (§6.3.3) — это не про
  вложенность транзакций, а про смешение двух политик полей.

**Почему блокировки не освобождаются преждевременно.**

`ROLLBACK TO SAVEPOINT` не снимает row-блокировки InnoDB: они удерживаются до
реального `COMMIT` / `ROLLBACK` транзакции верхнего уровня либо до отмены
транзакции сервером. Поэтому `lockForUpdate`, взятый внутри операции, защищает
её и после выхода из `run` в режиме присоединения — ровно то, что требуется для
атомарности набора полей и jobs.

**Запреты внутри операции.**

- `DB::commit()`, `DB::rollBack()`, `DB::beginTransaction()` — запрещены:
  управление транзакцией принадлежит только владельцу.
- `DB::transaction()` вокруг вызовов `CharacterTransaction` допустим только как
  осознанное решение владельца (например, `RefreshDatabase` в тестах); внутри
  самого механизма он не используется.
- Внешние вызовы (HTTP, файлы, backup) внутри `run` запрещены в обоих режимах.

**Тесты.**

`tests/Pest.php` подключает `RefreshDatabase` для всех Feature-тестов, поэтому
там механизм всегда работает в режиме присоединения — это штатный сценарий, и
он покрывается отдельно: операция внутри чужой транзакции не коммитит, при
ошибке откатывается только до savepoint, внешние изменения остаются целы.

Конкурентные тесты (`FOR UPDATE`, ожидание блокировки, параллельный откат) в
`RefreshDatabase` невозможны: данные теста не закоммичены и не видны второму
соединению, а блокировки висят до конца теста. Они выносятся в отдельный набор
вне обёртки транзакцией (`DatabaseTruncation` / `DatabaseMigrations`) и
запускаются только на MySQL.

### 6.4. Ручной перенос при 2+ персонажах

В кабинете, на странице «Мои персонажи», при наличии legacy-значений и
нескольких персонажей показывается блок «Игровые данные аккаунта не привязаны
к персонажу» со списком значений и выбором персонажа. Перенос выполняется тем
же сервисом (`LegacyGameDataImporter::transferTo($user, $character)`), пишется
в журнал и может быть отменён по `batch_id`.

Выбор персонажа — явное действие владельца; автоматическое назначение первому
персонажу запрещено (ADR-013 §2.10).

### 6.5. Проверка и восстановление

- До применения: `--report` и `--dry-run`, сверка чисел с ожидаемыми, включая
  количество `skipped_conflict` с разбивкой по полям: каждый конфликт должен
  быть объяснён, а не спрятан в общем числе пропусков.
- После применения: контрольные суммы — количество непустых `race`, `main_job`,
  `legend` в `game_characters` до и после; сверка контрольного `applied_hash`
  выборки записей журнала с пересчётом по фактическим значениям полей в БД;
  ручная сверка 5–10 аккаунтов, включая соответствие `legend` ↔ `legend_html`.
- Любое расхождение останавливает приёмку: сначала `--rollback={batch}`, затем,
  при необходимости, restore backup. Повторный `--rollback` того же пакета
  безопасен.
- Ошибка внутри транзакции аккаунта (deadlock, `lock wait timeout`, исключение)
  откатывает её целиком: журнал по этому аккаунту остаётся в прежнем статусе,
  данные не изменены, повторный запуск безопасен (§6.3.3). Ошибка одного
  аккаунта не блокирует обработку остальных и попадает в отчёт отдельной
  строкой.
- Восстановление: `--rollback={batch}` возвращает только значения, записанные
  импортом, к `target_value_before`; отчёт различает `reverted`,
  `skipped_modified` (изменено после импорта) и `skipped_conflict` (перенос не
  выполнялся). При расхождении контрольных сумм — restore backup.
- Legacy-колонки `users.*` **не удаляются** в этапах 0–5. Удаление — отдельная
  contract-миграция после подтверждённого переноса и периода наблюдения.

### 8.2. Новые сценарии

Доступ и права:

- гость → `/cabinet/characters` → redirect на login;
- пользователь без `section.players.view` → 403;
- пользователь без подтверждённого email → создание/изменение запрещено,
  список доступен;
- чужой персонаж: `show`, `update`, `delete` → 403;
- soft-deleted персонаж: `show` → 404;
- `user_id` в запросе игнорируется.

Игровые данные:

- создание с расой, main job и jobs сохраняет все строки;
- `main_job` вне списка jobs → ошибка валидации;
- jobs пуст и `main_job` задан → ошибка;
- уровень 0 / 100 → ошибка; пустое поле → job не сохраняется;
- легенда сохраняется как Markdown и рендерится в `legend_html`;
- правка легенды пересчитывает `legend_html`; неизменённая легенда не трогает
  HTML;
- легенда с небезопасной разметкой (`<script>`, `javascript:`-ссылка) не
  проходит через `ContentRenderer`; `legend_html` из запроса игнорируется;
- пустая легенда даёт `legend_html = null`;
- раса `null` отображается как «не указана»;
- деактивированный сервер: сохранение без смены сервера проходит, смена на
  неактивный — ошибка;
- создание персонажа на неактивном сервере — ошибка валидации;
- подстановка чужого/неактивного `game_server_id` в запросе обновления не
  обходит правило (сравнение с сервером из БД).

Навигация и совместимость:

- пункт «Мои персонажи» в кабинете стоит сразу после «Профиля»;
- пункта нет в `_sidebar` и `_section-nav`;
- `/players/characters` → 302 на `cabinet.characters.index`, query string
  сохраняется;
- POST на `/players/characters` → 405, данные не создаются;
- в реестре страниц нет записи `players.characters.index` и нет «missing»;
- RU и EN: страницы отдают корректные подписи в обеих локалях.

Данные и миграции:

- миграция добавляет только nullable-колонки; существующие строки не меняются;
- уникальность `(game_server_id, name)` включая soft-deleted сохраняется;
- `game_character_jobs` каскадно удаляется только при физическом удалении
  персонажа (force delete, удаление аккаунта). При soft delete строки jobs
  сохраняются вместе с персонажем — восстановление не теряет уровни;
- миграции этапа не содержат `dropColumn`, `renameColumn` и операций над
  `users`; `users.race`, `users.main_job`, `users.legend`, `users.legend_html`
  после реализации совпадают с исходными.

Подфаза 1.5:

- `--report` на фикстурах: 0 / 1 / 2+ персонажей дают ожидаемые числа;
- `--dry-run` не пишет в БД и показывает те же конфликты, что и `--report`;
- `--apply` переносит только в пустые поля и пишет журнал;
- журнал содержит `source_value`, `source_hash` (нормализованный),
  `applied_hash` и `target_hash_before` (контрольные) и
  `target_value_before = NULL` для пустых полей;
- `applied_hash` считается по значению из БД после записи и отличается от
  `source_hash`: это разные величины с разными правилами;
- непустое целевое поле → `skipped_conflict` с `target_value_before`; значение
  персонажа не изменилось, остальные пустые поля аккаунта перенесены;
- **разделение нормализации и контроля:** если после импорта `NULL` заменён на
  `''`, изменён регистр `race`/`main_job` или добавлен внешний пробел в
  `legend`, нормализованный хеш совпадает, а контрольный — нет; откат даёт
  `skipped_modified` и сохраняет значение пользователя;
- `--overwrite` сохраняет `target_value_before` и `target_hash_before`, а
  `--rollback` возвращает именно прежнее значение, а не `NULL`;
- `--overwrite` без значения перезаписывает `race`, `main_job`, `legend`;
  `--overwrite=race,legend` — только перечисленные;
- `--overwrite=legend_html`, `--overwrite=jobs`, `--overwrite=`,
  `--overwrite=unknown`, а также `--overwrite` без `--apply` — ошибка ввода
  без записи в БД;
- `--overwrite` не меняет ни одной строки `game_character_jobs`;
- нормализация импорта: `''` в источнике и `NULL` в персонаже не создают
  переноса; `legend` с CRLF не даёт ложного конфликта; `race` и `main_job`
  сравниваются без учёта регистра и внешних пробелов;
- `game_character_jobs`: существующий уровень job не перезаписывается;
  добавленный импортом job удаляется при откате только при совпадении
  контрольного хеша уровня; изменённый вручную — остаётся;
- группа `legend`/`legend_html` откатывается только при совпадении обоих
  контрольных хешей: изменённый HTML оставляет группу нетронутой целиком;
- `legend` переносится как Markdown, `legend_html` пересчитывается, а не
  копируется; legacy `users.legend_html` не используется;
- повторный `--apply` ничего не дублирует и не перезаписывает;
- `--rollback` восстанавливает `target_value_before` и не трогает изменённые
  вручную поля (`skipped_modified`);
- повторный `--rollback` того же пакета не меняет данные;
- **атомарность проверки и записи:** значение, изменённое параллельной
  транзакцией между чтением журнала и восстановлением, не затирается — откат
  видит его под блокировкой и даёт `skipped_modified`;
- **блокировки:** `--rollback` берёт `FOR UPDATE` по строке персонажа и по
  строке `(character_id, job)`; сохранение персонажа через кабинет сериализуется
  с откатом, а не пересекается;
- **параллельный двойной откат:** два запуска по одному `batch_id` не
  восстанавливают запись дважды — второй видит 0 затронутых строк
  (`UPDATE ... WHERE status = 'applied'`);
- **группа `legend`:** при изменённом `legend` или `legend_html` не меняется ни
  одно из полей; при сбое посреди транзакции оба остаются в состоянии до отката;
- **сбой и deadlock:** исключение внутри транзакции аккаунта оставляет и поля,
  и статусы журнала без изменений; повторный запуск даёт тот же результат;
  исчерпание повторов фиксируется как ошибка аккаунта, остальные аккаунты
  обрабатываются;
- **jobs при гонке:** конкурентное изменение уровня не приводит к удалению
  строки — `DELETE` с условием `level = ?` не находит совпадения;
- **единый механизм записи:** сохранение через кабинет, `--apply` и
  `--rollback` проходят через `CharacterTransaction`; попытка изменить
  персонажа в обход механизма (прямой `save`, `insert`, `DB::table(...)->update`,
  собственный `DB::transaction()`) обнаруживается тестами §8.3;
- **импорт и откат не через пользовательский сервис:** правила перезаписи и
  восстановления реализованы в `LegacyGameDataImporter` и
  `LegacyGameDataRollback`, а транзакция и блокировки берутся из общего
  механизма;
- **current read:** решение об откате принимается по значению, прочитанному
  locking read внутри транзакции: если строка изменена между загрузкой модели и
  откатом, используется новое значение, а не значение модели в памяти;
- **режим присоединения:** операция, вызванная внутри внешней транзакции
  (штатно — Feature-тест с `RefreshDatabase`), не коммитит её; при исключении
  откатывается только до своего savepoint, а изменения внешней транзакции
  остаются;
- **рекурсивный вход:** повторный `CharacterTransaction::run` изнутри
  выполняющейся операции даёт `LogicException`, а не тихую вложенную
  транзакцию;
- **повторы по владельцу:** deadlock/`lock wait timeout` повторяются только в
  режиме `transactionLevel() = 0`; в режиме присоединения исключение
  пробрасывается, операция не выполняется дважды;
- **ошибка аккаунта:** после исчерпания трёх попыток поля и статусы журнала по
  аккаунту не изменены (транзакция отката целиком), запись об ошибке сделана
  отдельной транзакцией и присутствует в отчёте;
- отчёт `--rollback` различает `reverted`, `skipped_modified` и
  `skipped_conflict`;
- ручной перенос при 2+ персонажах создаёт запись журнала с собственным
  `batch_id`.

### 8.3. Архитектурные и конкурентные проверки

Поиск строк по `app/` сам по себе ненадёжен: он даёт ложные срабатывания на
другие модели (`$user->update()`, mass-update Filament-таблиц) и пропускает
`insert()`, `upsert()`, `DB::table(...)->update()`, `saveQuietly()`,
`forceDelete()`, `increment()`. Поэтому границы защищаются тремя независимыми
уровнями, и ни один из них не является единственным.

**1. Чтение разрешено, запись ограничена (архитектурный тест).**

Ограничение накладывается не на использование моделей, а на способы изменения
данных.

- **Чтение разрешено везде:** `GameCharacter::query()`, scopes (`public`,
  `ownedBy`), `find`, `first`, `paginate`, `with('jobs')` и любые eager loading,
  отношения, `withTrashed`, чтение в контроллерах, Livewire, Blade, Filament
  (read-only), политиках, `CharacterContext` (этап 2), каталоге персонажей
  (этап 4) и новых сервисах отображения. Ни один архитектурный тест не запрещает
  `use App\Models\GameCharacter` для чтения.
- **Запись ограничена:** примитивы изменения (`create`, `insert`, `upsert`,
  `update`, `save`, `saveQuietly`, `delete`, `forceDelete`, `restore`, `push`,
  `increment`, `decrement`, `jobs()`-sync/attach/delete, `DB::table(...)`,
  `DB::statement`) разрешены только `CharacterTransaction`,
  `GameCharacterSaver`, `LegacyGameDataImporter`, `LegacyGameDataRollback`,
  фабрикам и сидерам.
- Любой другой класс с примитивом записи — падение теста. Список разрешённых
  задаётся явно, поэтому новый путь записи нельзя добавить молча.

**2. Примитивы записи (тест на обход механизма).**

Вне `CharacterTransaction` и фабрик/сидеров запрещены:

- `GameCharacter::create|insert|upsert|firstOrCreate|updateOrCreate`;
- `->save(`, `->saveQuietly(`, `->update(`, `->delete(`, `->forceDelete(`,
  `->restore(`, `->push(`, `->increment(`, `->decrement(` для персонажа;
- `DB::table('game_characters')`, `DB::table('game_character_jobs')`,
  `DB::statement(`, `DB::update(` по этим таблицам;
- запись jobs через `jobs()->create|save|sync|delete`.

Каждое найденное совпадение сопоставляется с разрешённым классом: корректные
операции внутри механизма не блокируются, а обход через `insert`/`upsert`/
`DB::table`/`saveQuietly` обнаруживается.

**Meta-тест сканера (обязателен).** Сам сканер проверяется на фикстурах:

- положительные примеры — `$character->save()`, `$character->update([...])`,
  `GameCharacter::upsert(...)`, `DB::table('game_characters')->update(...)`,
  `$character->jobs()->sync(...)` — должны быть найдены;
- отрицательные примеры — `GameCharacter::query()->where(...)->get()`,
  `$character->jobs`, `GameCharacter::with('jobs')->paginate()`,
  `$user->update([...])`, `DB::table('users')->update(...)` — не должны давать
  срабатываний.

Без этого теста сканер легко становится либо дырявым, либо запрещающим чтение.

**3. Поведенческие и конкурентные тесты.**

- **Точка входа:** контроллер и команда вызывают соответствующий сервис
  (подмена `CharacterTransaction` / `GameCharacterSaver` в контейнере и проверка
  факта вызова), прямой записи в обход нет.
- **Атомарность:** исключение в середине операции оставляет и персонажа, и
  jobs без изменений.
- **Несколько полей и jobs:** импорт и откат меняют набор полей и jobs в одной
  транзакции аккаунта — при сбое не остаётся частично применённого набора.
- **Владение и savepoints:** `run` на уровне 0 коммитит сам; `run` внутри
  внешней транзакции не коммитит и не откатывает её целиком, а при исключении
  откатывается только до своего savepoint; после такого отката внешняя
  транзакция продолжается, её изменения целы; рекурсивный вход внутрь
  выполняющейся операции даёт `LogicException` (§6.3.4);
- **Повторы:** deadlock и `lock wait timeout` повторяются только в режиме
  владельца; в режиме присоединения исключение пробрасывается владельцу, а не
  повторяется механизмом.
- **Блокировки:** тесты идут на MySQL (`phpunit.xml`: `DB_CONNECTION=mysql`,
  `db:3306`), поэтому `FOR UPDATE` проверяется реально, без замены заглушкой.
  Второе соединение держит блокировку — первая операция ждёт её снятия и
  получает актуальное значение.
- **Конкурентный откат:** изменение, сделанное вторым соединением после чтения
  журнала, приводит к `skipped_modified`, а не к потере правки.
- **Сбой посреди отката:** исключение не оставляет частично восстановленного
  аккаунта, статусы журнала не меняются.

Тесты конкурентности помечаются группой `concurrency`, выполняются на MySQL и
**вне обёртки `RefreshDatabase`** (`DatabaseTruncation` / `DatabaseMigrations`):
внутри тестовой транзакции данные не видны второму соединению, а блокировки
висят до конца теста, поэтому такая проверка была бы фиктивной. На другом
драйвере они пропускаются, а не подменяются заглушкой.

**Чтение не ограничено (проверка «наоборот»).** Отдельный тест подтверждает, что
архитектурные правила не мешают нормальной работе: класс, который только читает
персонажей (`GameCharacter::query()->with('jobs')->paginate()` в сервисе
отображения или Livewire-компоненте), проходит все проверки §8.3 без
исключений. Это защита от того, что правило «нет записи» превратится в правило
«нет доступа к модели».

2. Pint и Larastan без ошибок.
3. Ручная проверка на desktop (1440×900, 1280×720) и mobile (390×844).
4. RU и EN: отсутствие смеси языков и «сырых» ключей локализации.

9. В миграциях этапа нет `dropColumn`, `renameColumn` и операций над `users`;
   legacy-поля удаляются только отдельной contract-миграцией за пределами
   этапов 0–5.
10. Незакоммиченный Stage 0/1 Players и посторонние файлы рабочей директории
    сохранены: логика серверов, персонажей, Policy и фабрик не пересоздавалась.
11. Импорт и откат не теряют существующие данные персонажа: значения, не
    созданные импортом, остаются неизменными, а откат восстанавливает только
    `target_value_before` при совпадении **контрольного** хеша с `applied_hash`.
    Косметические ручные изменения (`NULL` → `''`, регистр, пробелы) не
    откатываются: нормализованный `source_hash` в решении об откате не
    участвует. Сценарии §8.2 это подтверждают.
12. Конкурентный откат безопасен: проверка контрольного хеша и восстановление
    выполняются в одной транзакции под блокировкой строки персонажа; правка,
    сделанная параллельно, не затирается; сбой (deadlock, исключение) не даёт
    частично восстановленного аккаунта, а повторный запуск безопасен.
13. Единый механизм записи: пользовательское сохранение, импорт и откат
    используют `CharacterTransaction`; собственных `DB::beginTransaction()` /
    `DB::transaction()` и `lockForUpdate()` по таблицам персонажей вне механизма
    нет. Владение транзакцией однозначно: на уровне 0 коммитит и откатывает
    механизм, внутри внешней транзакции — её владелец, а механизм откатывается
    только до своего savepoint; рекурсивный вход даёт `LogicException`. Тест
    примитивов записи и meta-тест сканера зелёные.
14. Актуальность данных и фиксация ошибок: откат принимает решение только по
    current read (locking read), а не по модели в памяти или snapshot
    `REPEATABLE READ`; ошибка аккаунта после исчерпания повторов записана вне
    отменённой транзакции, а уже откатанные аккаунты повторно не
    обрабатываются.
15. Атомарность набора: импорт и откат изменяют несколько полей и jobs в одной
    транзакции аккаунта; при сбое не остаётся частично применённого набора.
    Внутри внешней транзакции операция атомарна на уровне savepoint: откат
    затрагивает только её изменения, а не работу владельца.
16. Архитектурные и конкурентные проверки §8.3 выполнены: ограничение только на
    примитивы записи, meta-тест сканера, поведенческие тесты точки входа,
    владения и savepoint, тесты блокировок на MySQL. Конкурентные тесты
    запускаются вне обёртки `RefreshDatabase`; на другом драйвере пропускаются
    явно.
17. Чтение персонажей не ограничено: сервис, Livewire-компонент и шаблон,
    которые только читают `GameCharacter`/`game_character_jobs` (включая eager
    loading и scopes), проходят все архитектурные тесты без исключений; правило
    «нет обхода записи» не превращается в «нет доступа к модели».

## 15. Аудит, исправления и визуальная проверка (v1.9)

### 15.1. Аудит теста идемпотентности

Тест `it is idempotent for repeated apply and rollback` падал не из-за
импортёра. Причина — в самом тесте: `LegacyGameDataTransfer::query()->value('batch_id')`
не содержит `ORDER BY`, а индекс по `batch_id` позволяет вернуть любую строку,
поэтому откат применялся к произвольному batch (в том числе к тому, где все
записи — `skipped_conflict`).

Контракт этапа при этом не нарушен: каждый запуск создаёт свой batch, повторный
`--apply` не дублирует перенос и журналирует только конфликты.

Тест переписан детерминированно: batch берётся в порядке `id`, проверяются два
batch (4 записи `applied` + 3 `skipped_conflict`), после двойного отката —
4 записи `reverted` и пустые `race`, `main_job`, `legend`, `legend_html`.

### 15.2. UX-дефект ручного переноса

После успешного переноса блок «Игровые данные аккаунта не привязаны к
персонажу» оставался на странице. Значения `users.*` не очищаются (это
правильно), а `pendingFor()` проверял только наличие значений и число
персонажей — то есть утверждение «данные не привязаны» становилось неверным и
приглашало к повторному переносу.

Исправление: `pendingFor()` возвращает `null`, если для всех legacy-полей

## 16. Двуязычная легенда (v1.10)

### 16.1. Схема хранения

Легенда разделена на две независимые пары «Markdown + подготовленный HTML»:

| Колонка | Назначение |
|---|---|
| `legend_ru` / `legend_ru_html` | русская версия и её санитизированный HTML |
| `legend_en` / `legend_en_html` | английская версия и её санитизированный HTML |
| `legend` / `legend_html` | прежнее одно поле: **не изменяется** и **не удаляется** |

Миграция `2026_11_17_110000_add_localized_legends_to_game_characters_table`
только добавляет четыре nullable-колонки (expand-only, `down()` удаляет
исключительно их). Старые колонки остаются источником для проверки переноса и
страховкой: удаление — отдельное решение владельца после приёмки.

HTML каждой версии рассчитывается независимо через `ContentRenderer`
(Markdown + `HtmlSanitizer`), из запроса HTML никогда не принимается.

### 16.2. Перенос существующих легенд

Команда `characters:legend-locale` с режимами `--report`, `--dry-run`,
`--apply`. Определение языка — детерминированное (`App\Support\LegendLanguage`):
считается доля кириллических и латинских букв, решение принимается при
доминировании одного алфавита не менее 0,6; иначе текст считается неоднозначным.

Правила:

1. Источник (`legend`) **не изменяется и не очищается** — текст копируется.
2. Уже локализованная запись пропускается: повторный запуск безопасен.
3. `--apply` идёт через `CharacterTransaction` (блокировка строки), повторно
   проверяет отсутствие локализованной версии под блокировкой.
4. Неоднозначный текст сохраняется без изменений в RU (основная локаль сайта),
   чтобы остаться видимым; запись попадает в отчёт `--report`/`--dry-run` для
   ручной проверки. Перевода и дублирования в EN не происходит.

Фактический результат на рабочей БД после миграции: 2 персонажа, у одного
непустая легенда (1565 символов, английский текст) → `legend_en`; переносов в
RU — 0; неоднозначных — 0; legacy-колонка сохранена (1565 символов).

### 16.3. Интерфейс

- Форма персонажа содержит два независимых поля: «Легенда (RU)» и
  «Легенда (EN)»; при редактировании загружаются обе версии, а отсутствие ключа
  в запросе не сбрасывает сохранённый текст.
- Страница персонажа показывает **только** версию текущей локали
  (`GameCharacter::legendHtml(app()->getLocale())`); при отсутствии версии
  выводится пустое состояние, подстановки текста другого языка нет.
- Legacy-импорт аккаунта пишет перенесённую легенду и в локализованную колонку
  по тому же детектору; журнал переноса и откат покрывают локализованные поля.

`file_none`). Скрипты `initFileFields` и `initSubmitOnce` в
`resources/js/app.js` обновляют имя файла и исключают повторную отправку; при
возврате из bfcache состояние кнопки и имя файла восстанавливаются. Серверная
валидация загрузки не изменялась.

## 19. Header без белой полосы и локализация пунктов Footer (v1.13)

### 19.1. Причина белой полосы

`body > header` — `position: fixed; top: 0`, страница резервирует его высоту
через `body { padding-top: var(--header-height) }`. Логотип в шапке компактный
(`.logo-link .logo-wrap img { height: 40px }`), у шапки `padding: 8px 0`,
поэтому её фактическая высота — 56 px на desktop и 173 px на узком вьюпорте
(навигация складывается в колонку). При этом `--header-height` оставался
жёстким: 76 px на desktop и 120 px в `@media (max-width: 768px)`.

Итог: резерв на 20 px больше реальной высоты → под меню видна полоса цвета фона
страницы (`--bg-body`, в светлой теме белая); на мобильном наоборот — резерв
меньше высоты, и контент начинается под шапкой.

Полоса не связана с правками §17–§18: правило высоты логотипа и значение
76 px присутствуют уже в закоммиченной версии (`f510157`, `e602a5c`), где
`--header-height` не пересчитывался при уменьшении логотипа.

### 19.2. Исправление

Резерв больше не жёсткий: `initHeaderOffset()` в `resources/js/app.js` измеряет
`body > header` через `ResizeObserver` и записывает фактическую высоту в
`--header-height` — тот же приём, что `initFooterOffset()` для футера
(ADR-011 §2.23). Значение верно на любой ширине, при стековой раскладке
≤768 px и при смене локали: длина подписей меняет перенос строк и высоту.

Статическое значение в `:root` исправлено на фактическую высоту desktop-шапки
(56 px) и служит fallback до первого измерения и при отключённом JS. Значения
в media оставлены как fallback, runtime-измерение их перекрывает.

Header, меню, отступы, размеры и поведение не изменялись; отрицательных
отступов, наложений и дополнительных слоёв не добавлено.

Замеры (17.11.2026): `bodyPaddingTop − headerHeight = 0` на 1440×900,
1280×720 и 390×844; `scrollWidth − innerWidth = 0` на всех трёх.

### 19.3. Локализация пунктов Footer

Источник пунктов — `SiteNavigation` (ключ `footer.items` в настройках);
CMS-страницы попадают туда как `type=page` с сохранёнными `label_ru`/`label_en`.
У страниц `label_en` пуст, а `label()` подставлял русский `label_ru` — поэтому
на EN оставались «Правила сообщества» и «О сообществе».

Исправление: в `SiteNavigation::resolveItems()` для `type=page` подпись берётся
из самой страницы — `pageLabel(Page)`: `title_en` при `en`, иначе `title`
(per-field fallback, ADR-011 §2.20). Настройки навигации и URL не менялись,
дублирующих полей не создано. Правило действует и для header-навигации, если
там используется CMS-страница.

Результат: RU — «Правила сообщества», «О сообществе»; EN — `Community Rules`,
`About the Community`; остальные пункты (Контакты/Contacts,
Авторизация/Log in) не изменялись.

### 19.4. Тесты

## 20. Footer Editor — единственный источник подписей пунктов меню (v1.14)

### 20.1. Аудит архитектуры

- **Footer Editor** — Filament-страница управления футером; форма строится
  трейтом `ManagesNavigationItems`, пункт меню имеет канонический вид
  `{id, label_ru, label_en, type, target, visible, image}`. «Подпись (RU)» и
  «Подпись (EN)» — отдельные `TextInput`, у английского есть подсказка.
- **Хранение** — JSON-массив в `settings`: `footer.items` и `header.items`;
  чтение и запись идут через `App\Services\SiteNavigation`
  (`editableFooter()` для редактора, `footerItems()` для публичного вывода) и
  `App\Services\PageMenuManager::saveMenu()` при сохранении из админки.
- **Публичная разметка** — `resources/views/layouts/app.blade.php`, блок
  `<footer>`: ссылки и изображения из `SiteNavigation::footerItems()`.
- **Выбор языка** — `SiteNavigation::label()`: для `en` берётся `label_en`,
  для `ru` — `label_ru`; пустая английская подпись даёт `label_ru`
  (per-field fallback, ADR-011 §2.20).
- **Связь с CMS-страницей** — по `target` = ID страницы для `type=page`.
  Страница отвечает за URL (`page.show`), контент, `is_published` и
  `show_in_footer`; `order` и `image` принадлежат редактору меню.

### 20.2. Устранённое расхождение

В §19 публичный футер для `type=page` брал `Page.title_en` (метод
`pageLabel()`), обходя `label_en` из Footer Editor. Это создавало второй
источник перевода: правка английской подписи в редакторе не влияла на вывод,
а изменение `title_en` страницы меняло пункт меню.

Исправления:
1. `SiteNavigation::resolveItems()` использует `label($item)` для всех типов;
   `pageLabel()` удалён.
2. `PageMenuManager::save()` больше не перезаписывает заполненные подписи: при
   сохранении страницы подпись инициализируется только если она пуста;
   привязка по ID, `order` и `image` не затрагиваются.
3. Данные: пустые `label_en` пунктов CMS заполнены из `title_en` страниц
   (3 в header, 1 в footer). Это разовое заполнение содержимого настроек, а не
   новый механизм; после него кэш настроек (`settings.all`,
   `Cache::rememberForever`) сброшен — иначе публичный футер продолжал
   отдавать прежний массив.

### 20.3. Правило

| Локаль | Подпись в публичном футере | Источник |
|---|---|---|
| ru | `label_ru` | Footer Editor |
| en | `label_en`, если заполнена | Footer Editor |
| en | `label_ru`, если `label_en` пуста | per-field fallback (ADR-011 §2.20) |

Переключение языка меняет только подпись: `target`, URL, порядок, изображение
и состав пунктов остаются прежними. Пустая английская подпись не заменяется
названием страницы — используется русская подпись пункта. CMS-страница —
источник контента и данных целевой страницы, но не формулировок меню.

## 21. Двуязычная надпись футера (v1.15)

### 21.1. Аудит
