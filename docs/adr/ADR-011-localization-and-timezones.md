### 1.2. Продуктовая задача

Phoenix Server — международное сообщество игроков FFXI. На старте — два
языка (RU, EN) и участники из разных стран. Язык интерфейса, локальное
время пользователя и международное игровое время — **три независимые
сущности**; смешивание любой пары даёт неверные решения (например,
русскоязычный игрок в Японии обязан видеть время в Asia/Tokyo, а не в
Europe/Moscow).

## 2. РЕШЕНИЕ

### 2.1. Независимость языка и часового пояса

- `users.locale` — язык интерфейса.
- `users.timezone` — выбранный вручную часовой пояс.
- Переключение языка **не меняет** отображаемое время; смена пояса **не
  меняет** язык.
- Ни одна настройка не выводится из другой (никакой «пояс по локали»).

### 2.2. `LocaleResolver` — определение языка

**Приоритет для авторизованного пользователя:**

1. `users.locale` — сохранённый выбор в профиле.
2. Session — выбор, сделанный в текущей сессии (переключатель языка).
3. Cookie `locale`.
4. `Accept-Language` браузера — только как первичная подсказка.
5. `ru` — резервный язык сайта.

**Приоритет для гостя:**

1. Session — выбор в текущей сессии.
2. Cookie `locale`.
3. `Accept-Language` браузера.
4. `ru` — резервный язык сайта.

`users.locale` для гостя не рассматривается (пользователя нет). Порядок
«session → cookie» для гостя означает, что выбор, сделанный на текущем
визите, важнее ранее сохранённого cookie.

**Синхронизация при переключении языка:**

| Кто | Что обновляется | Условие успеха |
|---|---|---|
| Авторизованный | `users.locale` (профиль), затем session — в этом порядке | только после успешной записи `users.locale` |
| Гость | session **и** cookie `locale` | всегда (запись в БД не участвует) |

- Для авторизованного запись в `users.locale` выполняется только при
  явном переключении; автоматическое определение в профиль не пишется.
- **Авторизованный: переключение считается успешным только после
  успешного сохранения `users.locale`.** Session обновляется после
  записи в профиль, в той же операции.
- **При ошибке записи в профиль** переключение не считается выполненным:
  session **не** обновляется, пользователь получает сообщение об ошибке,
  интерфейс остаётся на прежнем языке (значение из `users.locale`).
  Конфликтующее значение в session не создаётся — иначе при следующем
  запросе `users.locale` с более высоким приоритетом отменил бы выбор из
  session, и состояние стало бы противоречивым.
- Session хранит только «текущий выбор», не является источником истины
  между визитами.

Правила:

- Поддерживаемые локали — `ru`, `en`; список расширяемый (конфиг/константа
  сервиса, не хардкод по файлам).
- Неизвестная или неподдерживаемая локаль безопасно приводится к `ru`;
  исключений не выбрасывается.
- Значения cookie, session и `users.locale` валидируются одинаково — по
  списку поддерживаемых локалей.
- Админка использует тот же резолвер; жёсткий `ru` в
  `SetAdminPanelLocale` заменяется на выбор админа с fallback `ru`.

### 2.3. `TimezoneResolver` — определение часового пояса

Приоритет:

1. `users.timezone` — ручной выбор в профиле (для авторизованного).
2. Cookie `tz` — IANA-зона браузера
   (`Intl.DateTimeFormat().resolvedOptions().timeZone`).
3. `UTC`.

Правила:

- Автоматически определённая зона **никогда** не записывается в
  `users.timezone`.
- Значение из cookie валидируется на сервере по
  `DateTimeZone::listIdentifiers()`; невалидное → `UTC`.
- Фиксированные смещения (`UTC+3`) не хранятся и не принимаются как
  значение пояса.
- Первый запрос гостя без cookie обслуживается в `UTC` с явной пометкой
  `(UTC)`; cookie ставится JS, принудительная перезагрузка страницы **не**
  выполняется. Со следующего запроса применяется пояс браузера.
- Резолвер безопасно работает без HTTP-контекста: CLI, queue, scheduler,
  тесты → `UTC` (нет `auth()`, нет cookie).

### 2.4. `TimezoneOptions`

Единый источник списка поясов для UI (профиль, форма события, админка):

- значения — IANA-идентификаторы (`Europe/Moscow`, `Europe/Berlin`,
  `Asia/Tokyo`, `America/New_York`, `UTC`);
- подписи — `Название (UTC ±N)`, где смещение вычисляется на момент
  рендера (учитывает DST и исторические переходы), а не хранится;
- список группируется по регионам; сортировка детерминирована.

**Реализовано в L1** (`App\Services\TimezoneOptions`, final, static):
`identifiers()` — отсортированный список IANA с `UTC` первым;
`grouped()` — `регион => [IANA => подпись]`, `UTC` первой группой;
`options()` — плоский список; `label()` — `Europe/Berlin (UTC +02:00)`;
`offset()` — текущее смещение через `now()->setTimezone()`; `isValid()` —
проверка вхождения в `DateTimeZone::listIdentifiers()`. Список и подписи
пересчитываются на каждый рендер (кеша нет).

### 2.5. Три семантики времени

Обязательное разделение; каждая семантика имеет свой механизм рендера.

**A. Календарная дата (calendar date).**

- Применяется: site-новости, даты публикаций, дата регистрации, галерея
  (`taken_at`), информационные страницы.
- Часовой пояс не применяется; дата не сдвигается при смене языка или
  пояса.
- Формат зависит от локали: RU `04.11.2026`, EN `Nov 04, 2026`.
- Компонент `<x-naive-date>`; параметров переключения семантики нет.

**B. Локальное время пользователя (user-local moment).**

- Применяется: чат, комментарии, уведомления, лента активности, сроки
  блокировок, прочие пользовательские события.
- Хранение — UTC; отображение — пояс зрителя.
- Для авторизованного ручной `users.timezone` приоритетнее браузера.
- Пометка пояса: для гостя — да (например `21:45 (Europe/Berlin)`);
  для авторизованного — как правило нет (это его личный контекст).
- Компонент `<x-datetime>`.

**C. Международное игровое время (international event time).**

- Применяется: игровые мероприятия, общие сборы, расписание активностей.
- Основной источник — UTC: `2026-11-07 18:00 UTC`.
- Все участники видят один и тот же момент; дополнительно допускается
  локальное время: `18:00 UTC · 21:00 Europe/Moscow`.
- UTC остаётся главным и неизменным; локальное — вторично.
- Локальное время показывается **всем зрителям, включая гостей**, но
  только при наличии валидного пояса (cookie `tz` либо `users.timezone`).
  Если пояса нет или значение некорректно — выводится **только UTC**, без
  дополнительной строки.
- Внутриигровое время Vana'diel — **отдельная семантика**, в этот ADR не
  входит.

### 2.6. `News::displayPublishedAt()`

Единый контракт отображения даты новости:

- `scope = site` → `published_at` — **календарная метка**; конвертация не
  применяется; формат — по локали (дата).
- `scope = player` → `published_at` — **реальный момент**; конвертируется
  через `TimezoneResolver`; формат — дата + время.
- Пустое значение → `—`.
- Семантика «редакционная дата» для site-новостей (frontend-spec §5.4) не
  меняется: видимость определяется `status = published` и
  `published_at IS NOT NULL`, отложенной публикации нет.

### 2.7. События (`events`)

- Хранение `starts_at` / `registration_close` — UTC (без изменений).
- Новая колонка `events.timezone` (`string(64)`, IANA) — пояс, в котором
  организатор объявил время. По умолчанию подставляется пояс организатора.
- Ввод: дата/время + явный пояс; серверная конвертация в UTC по правилам
  `PreparesEventDateTimes` (исправляется расхождение дефолтов).
- Вывод: UTC основным, локальное время зрителя — дополнительным; переход
  на следующие сутки показывается датой, а не только временем.
- Три пояса не смешиваются: пояс организатора (объявление), UTC
  (хранение/главное отображение), пояс участника (дополнительное
  отображение).
- Админка (`EventResource`) и публичная форма трактуют ввод одинаково.
- События, созданные до миграции, имеют `timezone = NULL`; backfill
  произвольным поясом **не выполняется** — такие события отображаются
  только в UTC.

**DST: несуществующее и неоднозначное локальное время.** При вводе
даты/времени в поясе объявления возможны два особых случая; оба должны
обрабатываться явно, без молчаливого выбора произвольного UTC-момента.

| Случай | Пример | Поведение |
|---|---|---|
| **Несуществующее** (spring forward) | `2026-03-29 02:30` Europe/Berlin — такого локального времени нет | Ввод отклоняется ошибкой валидации: «Указанное время не существует в выбранном часовом поясе (переход на летнее время). Выберите другое время или другой пояс». Запись не создаётся. |
| **Неоднозначное** (fall back) | `2026-10-25 02:30` Europe/Berlin — встречается дважды | Ввод отклоняется ошибкой валидации: «Указанное время неоднозначно в выбранном часовом поясе (переход на зимнее время). Укажите время после 03:00 или другой часовой пояс». Запись не создаётся. |

Правила:

- Проверка выполняется на сервере до сохранения (не только в UI).
- Запрещено использовать «первое» или «последнее» вхождение, `shiftTimezone`
  без проверки или приведение к UTC «как получится».
- Сообщение показывается в форме события (публичной и в админке) рядом с
  полем времени.
- При редактировании существующего события, сохранённого в UTC, проверка
  применяется только к новому вводу; хранимый UTC-момент не пересчитывается.
- Ввод в `UTC` не может быть несуществующим или неоднозначным — для пояса
  `UTC` проверка всегда проходит.

### 2.8. Системные журналы

- `admin_audit_logs`, backup-журнал, системные события и внутренние
  метки — **всегда UTC**, пометка `(UTC)`.
- Язык и пояс зрителя на них не влияют.
- `app.timezone = 'UTC'` сохраняется; глобальный
  `date_default_timezone_set()` запрещён.

### 2.9. Filament

- `FilamentTimezone::set(fn () => TimezoneResolver::for(auth()->user()))` —
  пользовательские timestamp-колонки и пикеры в поясе админа.
- Явный pin `->timezone('UTC')` обязателен для: `news.published_at`
  (поле **и** колонка), `photos.taken_at`, `admin_audit_logs.created_at`,
  backup-журнала; виджет последних аудит-записей рендерится через
  `<x-utc-datetime>`.
- `set()` и все pin-правки вводятся **одним коммитом**: промежуточное
  состояние сдвигает метки и аудит.
- Календарные метки в таблицах (`date()`) не конвертируются.

### 2.10. Blade-компоненты

Три отдельных тега, без параметра переключения семантики:

| Компонент | Семантика | Конвертация | Пометка |
|---|---|---|---|
| `<x-datetime>` | момент | в пояс зрителя | только для гостя |
| `<x-naive-date>` | календарная метка | нет | нет |
| `<x-utc-datetime>` | системное время | всегда UTC | `(UTC)` |

Разделение тегов — защита от случайного применения «момента» к метке.
Компоненты обязаны корректно работать в Blade, Livewire, Filament-виджетах
и при `null`-значениях (`—`).

### 2.11. Профиль пользователя

Два независимых поля:

| Поле | Тип | Правило |
|---|---|---|
| `users.locale` | `varchar(16) null` | `nullable`, `in:` список поддерживаемых локалей; `NULL` = авто (сессия → cookie → браузер → `ru`) |
| `users.timezone` | `varchar(64) null` | `nullable`, `timezone` (IANA); `NULL` = авто (cookie → `UTC`) |

- `users.locale` — `varchar(16)`, а не `varchar(5)`: запас под будущие
  локали с региональным суффиксом (`pt_BR`, `zh_Hans`, `es_419`). Список
  допустимых значений определяется `LocaleResolver`, а не длиной колонки;
  расширение RU/EN не требует миграции.
- Оба поля меняются независимо; UI — два отдельных контрола.
- Для существующих пользователей оба поля `NULL` → поведение не меняется
  (русский интерфейс, UTC-резерв).
- Автоматически определённые значения в профиль не пишутся.

**Реализовано в L1:** `App\Enums\Locale` (`ru`, `en` — единый источник
допустимых значений), `UpdateLocalePreferenceRequest`
(`present|nullable|string|max:16|in:ru,en`), `UpdateTimezonePreferenceRequest`
(`present|nullable|string|max:64|timezone`), `App\Services\LocalePreference`
(запись в БД, затем session), `App\Http\Controllers\PreferencesController` и
два независимых POST-маршрута в кабинете. `UpdateProfileRequest` **не
изменялся**: предпочтения не входят в основную форму профиля.

### 2.12. Legacy `timezone_display`

- `settings.timezone_display` **не удаляется** и не переименовывается до
  проверки всех зависимостей.
- В новой модели настройка не участвует в определении пользовательского
  времени; она сохраняется как исторический ключ и может быть удалена
  отдельным решением после подтверждённого отсутствия читателей.
- `timezone_display.ru` / `timezone_display.en` **не вводятся**.

### 2.13. URL-префиксы (`/ru/…`, `/en/…`)

Не внедряются в рамках этого ADR. Отдельное архитектурное решение:
требует проверки влияния на маршруты, signed URL, Filament, Livewire,
catch-all `/{page:slug}` и SEO (`hreflang`, `canonical`).

### 2.14. Ограничения реализации

- Запрещено менять `app.timezone` и вызывать
  `date_default_timezone_set()`.
- Запрещено «умное» определение пояса по IP, языку или геолокации.
- Обратная конвертация выполняется только на вводе (форма → UTC).
- Кеширование пояса в сессии не допускается: значение читается из
  пользователя/ cookie при каждом рендере. Session хранит только выбор
  языка (см. §2.2).

### 2.15. Охват локализации RU/EN

Локализация — целевое требование проекта, но выполняется отдельными
подэтапами (этап L5). Ниже — **явная граница**: что переводится, а что
остаётся непереведённым.

**Входит в локализацию:**

| Область | Что переводится |
|---|---|
| Публичные страницы | Главная, `/news`, `/news/{slug}`, `/gallery…`, `/events…`, статические страницы, `/cookie`, `/privacy` — весь пользовательский текст, включая кнопки, подписи, пустые состояния и placeholder'ы |
| Кабинет | Все вкладки (профиль, соцсети, новости, галерея, события, безопасность, опасная зона), формы, сообщения об успехе/ошибке |
| Auth | Регистрация, вход, восстановление пароля, верификация email, MFA-challenge — тексты и ошибки |
| Системные сообщения | Flash-сообщения контроллеров, `lang/{locale}/validation.php`, `auth.php`, `passwords.php`, `pagination.php` |
| Ошибки | Страницы 403/404/419/429/500 и сообщения валидации — на выбранном языке |
| Уведомления | Заголовки и тела database-уведомлений в колокольчике (письма не отправляются — все каналы `database`) |
| Админ-панель Filament | Интерфейс панели (меню, кнопки, подписи полей, фильтры, уведомления) через `lang/{locale}/filament.php` + vendor-переводы Filament; язык админа определяется тем же `LocaleResolver` |

**Не входит в локализацию (фиксируется явно):**

| Область | Причина / поведение |
|---|---|
| Пользовательский контент | Новости, комментарии, чат, легенды, описания событий, подписи фото — пишутся авторами на любом языке, не переводятся и не модерируются по языку |
| Названия игровых сущностей | Расы, job'ы, ранги, типы событий (сидируемые `title`) — остаются как в справочниках; перевод справочников не предусмотрен |
| Админ-данные | Значения `admin_audit_logs.action`, технические ключи, имена настроек — не переводятся |
| Письма | Почтовый канал не используется; при появлении — отдельная задача |
| URL | Языковые префиксы не вводятся (§2.13); slug'и не переводятся |
| Метаданные SEO | `meta_title`/`meta_description` — одно значение на сайт (не по локалям) |
| Filament-плагины/сторонние пакеты | Переводы берутся из vendor; отсутствующие строки остаются на английском |
| Внутриигровое время Vana'diel | Отдельная семантика, не входит |

**Правила:**

- Язык по умолчанию — `ru`; отсутствующий перевод падает на `ru`, а не на
  английский (осознанный выбор: сайт русскоязычного сообщества).
- `fallback_locale` в `config/app.php` приводится в соответствие с этим
  правилом на этапе L5; сейчас фактически `en` (зафиксировано в §1.1).
- `Carbon::setLocale()` включается только после завершения перевода
  (L5.8), иначе относительные даты станут русскими при английском UI.
- Частичная локализация недопустима как конечное состояние: экран не
  должен содержать смесь языков.

## 3. ПРИЧИНЫ

1. **Корректность.** Смешивание языка и пояса даёт неверное время для
   международной аудитории (русскоязычный в Японии, англоязычный в
   России).
2. **Предсказуемость.** Единственный источник момента — UTC в БД; все
   преобразования — на границе отображения и ввода.
3. **Сохранность данных.** Метки (`published_at` для site-новостей,
   `taken_at`) не должны «плыть» при смене настроек — иначе меняется
   сортировка ленты и содержимое архивов.
4. **Аудит.** Юридически и технически значимые записи обязаны быть
   сопоставимы между собой и не зависеть от настроек зрителя.
5. **Расширяемость.** Новый язык — запись в `lang/{locale}` и в список
   поддерживаемых; новые пояса — не требуют изменений кода (IANA).
6. **Совместимость.** `NULL` в новых полях = текущее поведение; миграция
   не меняет привычный опыт существующих пользователей.

## 8. РЕШЁННЫЕ ВОПРОСЫ

Все три вопроса закрыты владельцем 2026-11-04.

1. **`events.timezone` для существующих событий.** Записи, созданные до
   миграции, **не мигрируются** в произвольный пояс. `NULL` = «пояс не
   зафиксирован»; такие события отображаются **только в UTC** (§2.7).
2. **Локальное время события.** Показывается **всем зрителям, включая
   гостей**, если известен валидный пояс (cookie `tz` или
   `users.timezone`). При отсутствии cookie или некорректном значении —
   **только UTC** (§2.5C).
3. **Формат EN-даты.** `Nov 04, 2026` (§2.5A).

## 10. КРИТЕРИИ ПРИЁМКИ

**Статус выполнения (2026-11-05):** п. 13 выполнен в L1 (DONE / ACCEPTED);
п. 11 и 16 соблюдены (инварианты не нарушены). Остальные критерии относятся
к L2–L6 и на момент L1 **не выполняются** — соответствующие механизмы ещё
не реализованы.

1. Смена языка не меняет отображаемое время; смена пояса не меняет язык.
2. Гость: пояс браузера с пометкой; без cookie — `UTC` с пометкой.
3. Авторизованный с `users.timezone` — его пояс без пометки, приоритет над
   браузером.
4. Авторизованный без `users.timezone` — браузер → UTC; в профиль
   автоматически не пишется.
5. Невалидный IANA (cookie или БД) → безопасный fallback, без 500.
6. Календарные даты не сдвигаются; формат по локали (RU `04.11.2026`,
   EN `Nov 04, 2026`).
7. `scope=player` новости — момент, конвертируется.
8. События: UTC основным; локальное дополнительным **всем зрителям,
   включая гостей**, только при валидном поясе; без пояса — только UTC;
   переход суток корректен; `timezone = NULL` у старых событий → только
   UTC.
9. DST: несуществующее и неоднозначное локальное время отклоняются с
   понятной ошибкой; произвольный UTC-момент не выбирается.
10. Аудит и backup — UTC + `(UTC)`, независимо от языка и пояса.
11. `app.timezone = 'UTC'` не изменён; `date_default_timezone_set()` не
    используется.
12. Filament: пользовательские колонки в поясе админа; метки и аудит — UTC.
13. Профиль содержит два независимых поля (`locale` `varchar(16)`,
    `timezone` `varchar(64)`).
14. Приоритет языка: auth — `users.locale` → session → cookie →
    `Accept-Language` → `ru`; гость — session → cookie → `Accept-Language`
    → `ru`. Переключение авторизованным успешно только после записи
    `users.locale`, затем обновляется сессия (при ошибке записи сессия не
    меняется, показывается ошибка); гостем — сессия и cookie.
15. Охват локализации соответствует §2.15: переведены публичные страницы,
    кабинет, auth, системные сообщения, ошибки, уведомления, админ-панель;
    непереводимые области перечислены явно.
16. URL-префиксы не внедрены.
17. Тесты покрывают резолверы, компоненты, новости, события (включая DST),
    аудит, локализацию.
