---

## 1. ПРОБЛЕМА

Stage 7 включает события, чат, activity, bell и виджеты. Анализ
`frontend-spec.md` выявил 9 развилок, часть из которых противоречива или
не определена. До начала реализации их необходимо зафиксировать
как контракт, чтобы избежать «плывущих» решений.

---

## 2. РЕШЕНИЯ

### 2.1. Повторная запись на событие — одна строка на (event, user)

**Контекст:** `frontend-spec.md` §5.7 задаёт
`unique(event_id, user_id)` и одновременно утверждает, что «повторная
запись создаёт новую строку». Взаимоисключающие требования.

**Решение:** одна строка на пару (event, user). При выходе — статус
`left`, `left_at = now()`. При повторной записи — та же строка,
статус `joined`, `joined_at` перезаписывается, `left_at = null`.
Историю повторных входов/выходов не сохраняем в MVP.

**Последствия:** проще схема, проще запросы «кто идёт», нет дублей.
Минус: не сохраняется история «сколько раз пользователь перезаписывался».
Для community-портала это не критично.

### 2.2. Гостевой CTA — не на /players

**Контекст:** §6.7 упоминает гостевой дашборд с CTA «Войти», но
§3.1–3.6 запрещает гостю `/players*`. Противоречие.

**Решение:** `/players` — только auth. CTA «Войти» на страницах
`/events` и `/events/{event}` для гостей (если включено
`guest_sections.events`). В §6.7 спеки — неточность, фиксируем здесь.

### 2.3. Retention активности — от created_at, без каскадного удаления

**Решение:** `activity_retention_days` (default 180) считаем от
`activities.created_at`. Activity с удалённым субъектом остаются,
но ссылка на субъект не рендерится (аналогично «[аккаунт удалён]»).

### 2.4. FK-стратегия

| Таблица | FK | Стратегия |
|---|---|---|
| `events` | `user_id` | `nullOnDelete` |
| `event_participants` | `event_id` | `cascade` |
| `event_participants` | `user_id` | `cascade` |
| `chat_messages` | `user_id` | `nullOnDelete` |
| `activities` | `actor_id` | `nullOnDelete` |
| `activities` | `subject_*` | полиморф, без FK |

### 2.5. Модерация чата — admin-only

**Решение:** `chat.moderate` доступен только роли `admin` на Stage 7.
Расширение на `editor` — отдельный ADR, если понадобится.

### 2.6. Notifications и reminders

Обычные пользовательские уведомления (комментарий, ответ, mention,
запись/выход из события, отмена, одобрение/отклонение) отправляются
синхронно (как в Stage 6).

Reminder'ы о событиях запускаются scheduler'ом раз в минуту, кладут job
в `database` queue; внутри job формируется Laravel database notification
получателю. Здесь `database` queue driver — механизм запланированной
обработки job (запись в `jobs`); Laravel database notifications — отдельный
механизм хранения уведомлений в таблице `notifications`.

Идемпотентность reminder обеспечивается проверкой ранее отправленного
уведомления в database notifications. Конкретный механизм защиты от
конкурентного повторного запуска (атомарная вставка с уникальным индексом,
DB-транзакция, pessimistic lock или иная стратегия) определяется при
реализации D7. Новая таблица для этого заранее не добавляется без
необходимости.

### 2.7. Scheduler — Laravel 13 `withSchedule()`

**Решение:** регистрация задач в `bootstrap/app.php` через
`->withSchedule(...)` или в `routes/console.php` через `Schedule::call`.
Точный выбор — при реализации D7.

### 2.8. Граница Stage 7 / Stage 8 — api_chart и html_board в Stage 8

**Решение:** Stage 7 — только 4 widget'а: `community_chat`,
`events_board`, `activity_feed`, `online_users`. `api_chart` и
`html_board` — Stage 8 (Filament-настройки + Chart.js).

### 2.9. Пакеты — ничего нового

**Решение:** новых пакетов не устанавливаем. Livewire 4.4 уже есть.
Chart.js — при реализации `api_chart` в Stage 8.
WebSockets / Redis / SSE не используются.

## 3. ПОСЛЕДСТВИЯ

### 3.1. Положительные

- Все 9 развилок зафиксированы до начала реализации.
- Схема событий непротиворечива (2.1).
- Границы с Stage 8 определены (2.8).

### 3.2. Отрицательные и принятые риски

- §5.7 `frontend-spec.md` отклоняется в части «повторная запись новой
  строкой» (2.1). При следующей редакции spec — обновить.
- §6.7 `frontend-spec.md` отклоняется в части гостевого dashboard (2.2).
  При следующей редакции spec — обновить.
- Защита reminder от конкурентного повторного запуска остаётся предметом
  реализации D7; проверка существующего уведомления сама по себе не
  гарантирует exactly-once доставку (2.6).

---

## 4. УСЛОВИЯ ПЕРЕСМОТРА

- Требование хранить историю повторных записей на события (2.1).
- Необходимость модерации чата для editor'ов (2.5).
- Включение `api_chart` / `html_board` в MVP (2.8).
- Изменение механизма идемпотентности reminder при D7 (2.6).
