# ADR-010: Поведение гостя при закрытой секции Матрицы доступа

| Поле | Значение |
|---|---|
| Статус | Принят |
| Дата | 2026-10-23 |
| Этап | Вне этапа — правило доступа к публичным секциям |
| Связанные разделы | frontend-spec.md §3.6, §4, §8.4, §9.17; context.md §13; ADR-007 §2, §5.3 |
| Причина выделения | Требование владельца: закрытая для гостя секция должна предлагать авторизацию, а не отдавать 404 |

---

## 1. ПРОБЛЕМА

Матрица доступа (ADR-007) регулирует доступ к публичным секциям через
spatie-разрешения `section.{key}.view` (для ролей) и JSON `guest_sections`
в `settings` (для гостей). Middleware `section.access:{key}` при отсутствии
доступа у гостя отдавал **404 Not Found** — это было зафиксировано в
`frontend-spec.md` §3.6 п.1 и §9.17 п.17.

Практические следствия текущего поведения:

1. Гость, открывший закрытую секцию (например `/events`), видит «страница не
   найдена» и не понимает, что раздел существует и доступен после входа.
2. Поведение расходится с маршрутами, защищёнными `auth` (`/players*`,
   `/activity`, `/cabinet*`): там гость получает редирект на `/login` с
   сохранением `intended`. Один и тот же класс ситуаций («нужен вход»)
   обрабатывается двумя разными способами.
3. Владелец зафиксировал требование: на всех страницах, доступ к которым
   ограничен через Матрицу доступа, гостю предлагается авторизация.

ADR-007 §5.3 прямо предусматривает этот случай как условие пересмотра:

> Обнаружение несоответствия между middleware и тестовым сценарием
> `frontend-spec.md §9.17` (матрица: снятие флага → 403, снятие гостевого →
> 404).

Поэтому решение оформляется **новым ADR**, а не правкой ADR-007.

---

## 2. РЕШЕНИЕ

Поведение middleware `section.access:{key}` для **гостя** при закрытой секции
(`guest_sections[key]` отсутствует или равно `false`):

| Запрос | Ответ |
|---|---|
| GET/HEAD, HTML (`Accept` без JSON) | `302` redirect на `/login` + flash `status` |
| GET/HEAD, JSON (`expectsJson()`) | `403 Forbidden` |
| POST/PUT/PATCH/DELETE (любой формат) | `403 Forbidden` |

Дополнительные правила:

1. **Сообщение гостю** — «Для доступа к этому разделу требуется авторизация.»
   передаётся через существующий механизм `session('status')` и выводится
   текущим блоком в `resources/views/auth/login.blade.php`. Правок Blade не
   требуется.
2. **Сохранение исходного URL** — выполняется штатным
   `Redirector::guest()`: для GET исходный URL попадает в `intended`, после
   входа `LoginController` возвращает пользователя на него через
   `redirect()->intended()`. Для **HEAD** сохранение исходного URL **не
   гарантируется** (фреймворк сохраняет `previous()`); нестандартная логика
   сохранения не добавляется.
3. **Права после входа** — исходный URL открывается только при наличии
   `section.{key}.view`. Если разрешения нет, срабатывает существующая ветка
   middleware → `403`. Привилегия не повышается.
4. **Авторизованный пользователь** — поведение не меняется: admin проходит,
   остальные проверяются по `section.{key}.view`, при отсутствии — `403`.
5. **Не-GET запросы** — действие не выполняется, возвращается `403`; адрес
   изменяющего запроса в `intended` не сохраняется.
6. **Область применения** — только middleware `section.access`. Существующие
   `404` для отсутствующих объектов, закрытых профилей, скрытого приватностью
   или модерацией контента **не меняются**.
7. **Маршруты, защищённые `auth`** (`/players*`, `/activity`, `/cabinet*`, все
   POST-действия группы `events`) до `section.access` не доходят: `auth`
   имеет приоритет в `Illuminate\Foundation\Http\Kernel::$middlewarePriority`.
   Их поведение (redirect на `/login`) сохраняется без изменений.

## 3. АЛЬТЕРНАТИВЫ

| Вариант | Решение |
|---|---|
| Оставить `404` (текущее поведение) | Отклонён: владелец требует предлагать авторизацию; расходится с поведением `auth`-маршрутов |
| Всегда редиректить на `/login`, включая JSON и не-GET | Отклонён: JSON-клиент получит HTML-редирект вместо ошибки; для изменяющих запросов редирект маскирует отказ |
| Всегда отдавать `403` с CTA-страницей | Отклонён: гость — не «запрещённый» пользователь; нужен вход, а не отказ |
| Отдавать `404` для гостя, но с ссылкой на вход | Отклонён: смешивает «объект не найден» и «нужен вход»; ломает различие, зафиксированное в §8.4 |
| **GET/HEAD HTML → `/login` + intended; JSON и не-GET → 403 (принято)** | **Принят** |

## 4. ПОСЛЕДСТВИЯ

### 4.1. Положительные

- Единое правило для всех секций Матрицы: «нужен вход» → страница входа.
- Поведение согласовано с маршрутами, защищёнными `auth`.
- После входа пользователь попадает на запрошенную страницу (для GET).
- Права проверяются после аутентификации: `403` при отсутствии
  `section.{key}.view`.
- Изменяющие запросы не выполняются и не сохраняются в `intended`.

### 4.2. Отрицательные и принятые риски

1. **Закрытые разделы перестают быть «невидимыми»** — гость узнаёт о
   существовании страницы. Принято осознанно: цель — предложить авторизацию.
2. **HEAD не гарантирует `intended`** — ограничение `Redirector::guest()`;
   обход не реализуется, чтобы не вводить нестандартную логику.
3. **JSON-клиенты получают `403` вместо прежнего `404`** — изменение контракта
   для не-HTML потребителей; принято как корректное.
4. **`session('status')` делит канал** с сообщениями сброса пароля —
   теоретическая коллизия текста, не функциональная.
5. **Защитная ветка для не-GET** срабатывает только если изменяющий маршрут
   окажется в секционной группе без `auth`; сейчас таких маршрутов нет.

### 4.3. Условия пересмотра

- Появление публичных секций, для которых факт существования страницы должен
  быть скрыт от гостя (тогда — отдельный флаг секции, новый ADR).
- Изменение поведения `Redirector::guest()` в мажорной версии Laravel.
