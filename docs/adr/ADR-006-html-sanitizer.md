# ADR-006: Выбор HTML-санитайзера для рендера пользовательского контента

| Поле | Значение |
|---|---|
| Статус | Принят |
| Дата | 2026-10-01 |
| Этап | 4 — Content engine (context.md §30) |
| Связанные разделы | frontend-spec.md §6.10, §9 (XSS-датасет); context.md §13 |
| Источник | анализ https://github.com/ezyang/htmlpurifier, PHP docs DOMDocument |

---

## 1. ПРОБЛЕМА

Пользовательский Markdown-контент (`news.body`, `pages.body`, `legend`,
`html_board`, описания событий) должен рендериться в безопасный HTML.
Нельзя допустить выполнения XSS через `<script>`, `javascript:`-ссылки,
`<iframe>`, `<style>`, SVG, событийные атрибуты (`onclick`, `onerror`),
`data:text/html`, entity-обходы (`javascript&colon;`) и т.д.

Пайплайн по frontend-spec.md §6.10:

1. **CommonMark** — Markdown → HTML. Установлен `league/commonmark 2.10.3`.
2. **HtmlSanitizer** — второй слой защиты: whitelist-фильтрация HTML.
3. **Post-processing** — внешним ссылкам `rel="nofollow noopener noreferrer"`
   и `target="_blank"`.

Вопрос: какой инструмент использовать для слоя 2?

---

## 2. РЕШЕНИЕ

Реализуем **собственный `App\Services\HtmlSanitizer`** на базе
`\DOMDocument` (встроен в PHP).

Никаких сторонних пакетов (`ezyang/htmlpurifier` не подключаем).

---

## 3. ПРИЧИНЫ

### 3.1. Whitelist у нас фиксированный и небольшой

Разрешённые теги (frontend-spec.md §6.10):

    p, br, strong, em, del, ul, ol, li, blockquote, code, pre, h2, h3, h4, hr, a

`<img>` в теле **запрещён** (только через обложки/галерею).

Такой маленький whitelist реализуется DOM-обходом в ~80 строк кода.

### 3.2. DOMDocument встроен в PHP

Не требует установки. Не добавляет зависимость в `composer.json`.
Не создаёт поверхность атаки через supply-chain.

### 3.3. Меньше контроля у сторонних пакетов

`ezyang/htmlpurifier` — зрелый, но:
- последний стабильный релиз 2022 года, обновления редкие;
- конфигурация через свой DSL (не наш whitelist);
- тянет HTMLPurifier_Config, CSSDefinition и т.п. — сложнее для аудита;
- в контексте одного разработчика на годы — дополнительная цепочка
  обновлений.

### 3.4. Никакого raw-HTML от пользователей в принципе

Мы **не отдаём** пользователям возможность сохранять произвольный HTML.
Markdown рендерится через `html_input => 'strip'` (CommonMark уже
удаляет raw HTML до нашего санитайзера). Наш санитайзер — **вторая линия
защиты**, а не единственная.

---

## 4. АЛЬТЕРНАТИВЫ

| Вариант | Решение |
|---|---|
| `ezyang/htmlpurifier` | Отклонён: старая кодовая база, избыточная функциональность, свой конфиг-DSL. |
| `meowsolutions/sanitizer` | Отклонён: сторонний пакет, требует проверки; выигрыша нет. |
| `symfony/html-sanitizer` | Отклонён: тянет symfony-компоненты; для нашего whitelist избыточен. |
| Ничего не делать, полагаться только на CommonMark | Отклонён: CommonMark `html_input => 'strip'` защищает от raw HTML, но **не** от опасных ссылок (`[x](javascript:)`) — их надо фильтровать после рендера. |
| Собственный DOMDocument | **Принят.** |

---

## 5. ПОСЛЕДСТВИЯ

### 5.1. Положительные

- Нет новой зависимости в `composer.json`.
- Whitelist полностью под нашим контролем и явно читается в коде.
- Кросс-совместимость: DOMDocument есть в любом PHP 8.4.
- Покрытие XSS-датасета (frontend-spec.md §9) обеспечивается
  unit-тестом `tests/Unit/HtmlSanitizerTest.php`.

### 5.2. Отрицательные / принятые риски

- Свой санитайзер требует **поддержки**. Изменения whitelist
  делаются явно в коде, а не в конфиге. Это компенсируется unit-тестом
  с полным XSS-датасетом.
- **Не покрываем** сложные случаи вроде CSS-инъекций внутри `<style>`
  — потому что `<style>` полностью удаляется.
- **Не покрываем** атаки на уровне браузера (mXSS на старых движках) —
  но их не покрывает и htmlpurifier.

### 5.3. Условия пересмотра

- Появление CVE в DOMDocument (крайне маловероятно, часть PHP core).
- Обнаружение обхода санитайзера на XSS-датасете — сначала фиксим
  санитайзер, ADR пересматривается только если класс атак системный.

---

## 6. РЕАЛИЗАЦИЯ

`App\Services\HtmlSanitizer::sanitize(string $html): string`.

Алгоритм:

1. Обернуть фрагмент в `<div>`-обёртку, загрузить в `DOMDocument`
   (`LIBXML_HTML_NOIMPLIED | LIBXML_HTML_NODEFDTD`).
2. Рекурсивно обойти дерево:
   - теги вне whitelist — заменить на текст (`nodeValue`) или удалить;
   - опасные теги с содержимым (`script`, `iframe`, `style`, `svg`,
     `form`, `object`, `embed`) — удалить целиком;
   - атрибуты: оставить только `href` у `<a>` (валидные схемы:
     `http`, `https`, `mailto`), всё остальное (включая `on*`, `style`,
     `class`, `id`, `data-*`) — удалить;
   - запрещённая схема — заменить ссылку на её текст.
3. Внешним ссылкам добавить `rel="nofollow noopener noreferrer"
   target="_blank"`.

Все тесты — `tests/Unit/HtmlSanitizerTest.php` с XSS-датасетом
(frontend-spec.md §9).
